1. 개요·범위: 두 인증 체계와 세션의 적용 범위

이 저장소에는 인증 체계가 둘 있다. API(/api/...)는 OAuth2 password 흐름으로 받은 JWT Bearer access 토큰을 쓰고, 관리 화면(/admin, SQLAdmin)은 서명된 세션 쿠키 admin_session을 쓴다. 둘은 저장 위치·수명·폐기 방식이 다르고 서로를 대신하지 않는다.

확인 결과 — 세션은 /admin 전용이다(admin-login ADR-008). 앱 전역 SessionMiddleware는 없다. 세션 미들웨어는 SQLAdmin 하위 앱(/admin 마운트) 안에만 있고, API 의 인증 의존성 get_current_principal은 Authorization: Bearer 헤더만 본다(app/core/security/dependencies.py:31 oauth2_scheme, :66). SESSION_COOKIE_NAME(기본 session)은 접속 로그 미들웨어가 쿠키 값을 session_id 열에 기록용으로만 읽는다(app/core/middlewares/user_info_middleware.py:57, :174) — 인증에 쓰지 않는다. Celery 태스크·스크립트도 세션을 쓰지 않는다.

이 확인은 테스트로 고정돼 있다: tests/test_admin_login.py 의 test_session_middleware_lives_only_in_the_admin_sub_app(메인 앱 user_middleware에 없음, 하위 앱에만 있음), test_admin_session_cookie_does_not_authenticate_the_api(유효한 admin_session 쿠키만으로 /api/v1/auth/me는 401), test_admin_session_cookie_is_never_set_outside_admin(/admin 밖 응답은 이 쿠키를 설정하지 않음), 그리고 위 쿠키가 실제로 유효한 관리 세션임을 보이는 대조군 test_crafted_cookie_is_a_valid_admin_session.

SESSION_SECRET_KEY의 소비처는 정확히 둘이다: ① 관리 세션 쿠키 서명 키 — app/features/admin.py:96(build_admin_auth_backend), ② 설정 검사 — config.py:1263(.env 없을 때 필수 환경 변수 목록), config.py:1357(placeholder·길이 검사). 그 밖의 코드는 이 키를 읽지 않는다.

2. 구성도와 주입 관계

메인 FastAPI 앱의 미들웨어 체인을 지난 요청은 경로에 따라 갈린다. /api는 라우터와 JWT 의존성으로, /admin은 SQLAdmin 이 만든 Starlette 하위 앱으로 간다. 관리 세션 미들웨어는 그 하위 앱의 미들웨어로만 등록된다 — sqladmin 이 authentication_backend.middlewares를 하위 앱 생성에 넣는다(sqladmin 0.32 Admin.__init__). 그래서 /api 요청은 세션 미들웨어를 지나지 않는다.

협력 객체는 모두 생성자 주입이다. 조립은 app/features/admin.py 한 곳이 하고(build_admin_auth_backend :84, create_admin_interface :101), 테스트는 authentication_backend= 인자로 세션 팩토리·Redis 만 바꾼 백엔드를 넣는다. Redis 는 lifespan 이 app.state.redis 에 두므로 생성 시점이 아니라 로그인 시점에 꺼낸다 — 하위 앱 안의 request.app은 메인 앱이 아니라서 get_redis(request)를 쓸 수 없다(:94). 자격 확인은 API 로그인과 같은 verify_credentials를 쓴다(app/features/auth/services/auth_service.py:29).

코드 근거: admin.py · create_admin_interface · admin_auth.py · AdminAuthBackend · main.py

3. 기동 결정 흐름: ADMIN 잔존 검사와 ADMIN_DISABLED 분기

예전 설정 ADMIN(true=켬)은 ADMIN_DISABLED(true=끔, 기본 false)로 바뀌었다(ADR-006). Settings 는 extra="ignore"라 남은 ADMIN을 조용히 버리는데, 그러면 ADMIN을 false로 두어 끄려던 배포가 관리 화면을 켠 채 뜬다. 그래서 validate_renamed_settings()(config.py:1296)가 환경 변수와 .env 키를 대소문자 무시로 보고, 남아 있으면 기동을 멈춘다. 호출 순서는 config.py:1412~:1414(validate_env_source → validate_renamed_settings → validate_deployment_safety). ENV=test는 다른 검사와 마찬가지로 건너뛴다.

main.py:342~:352가 분기한다. ADMIN_DISABLED=true면 app.features.admin을 import 하지 않으므로 sqladmin·AdminAuthBackend·관리 세션 미들웨어가 하나도 만들어지지 않는다(ADR-007).

4. 로그인 시퀀스

로그인 화면은 app/templates/admin/sqladmin/login.html이다. sqladmin 은 템플릿 로더를 ChoiceLoader([FileSystemLoader(templates_dir), ..., PackageLoader("sqladmin", "templates")]) 순서로 만들므로(sqladmin 0.32 Admin.init_templating_engine) templates_dir의 같은 이름 파일이 기본 화면을 덮어쓴다. 경로는 ADMIN_TEMPLATES_DIR(app/features/admin.py:81). 화면은 base 를 확장하지 않는 독립 HTML 이며 Bootstrap 5.3.8 CSS 만 SRI(sha384-sRIl4kxILFvY47J16cr9ZwB07vP4J8+LH7qKQnuqkuIAvNWLzeN8tE5YBujZqJLB)로 불러온다. JavaScript 는 없다(ADR-005).

  1. 폼 username/password 를 읽고 ClientIPResolver로 IP 를 정한다(admin_auth.py:92~).
  2. IP 키(AUTH_LOGIN_IP_MAX_ATTEMPTS, 기본 20)와 IP+사용자명 키(AUTH_LOGIN_MAX_ATTEMPTS, 기본 5)를 창 AUTH_LOGIN_WINDOW_SECONDS(기본 60초) 동안 센다(:100~:111). 접두사 admin:rl:로 API 로그인과 따로 센다(ADR-004).
  3. verify_credentials가 사용자 부재여도 더미 해시로 같은 비용의 검증을 치르고(auth_service.py:42), 옛 bcrypt 해시가 맞으면 Argon2 새 해시로 UPDATE 한다(:47, password_hasher.py:42). 백엔드가 그 UPDATE 를 commit 한다.
  4. 슈퍼유저가 아니면 실패(admin_auth.py:120). 성공이면 사용자 키 카운터를 지우고 session.clear() 후 user_id만 넣는다(:127~:129, 세션 고정 방지).
  5. sqladmin Admin.login이 True 를 받아 /admin/으로 302 를 보내고, 세션 미들웨어가 서명 쿠키를 붙인다.

코드 근거: admin_auth.py · login · auth_service.py · verify_credentials · rate_limiter.py · RateLimiter · login.html

5. 요청별 인증 흐름

sqladmin 의 login_required 데코레이터(sqladmin 0.32 sqladmin.authentication.login_required)가 관리 뷰마다 authenticate를 부른다. 쿠키의 서명·만료는 starlette SessionMiddleware가 먼저 확인하고, 실패하면 빈 세션으로 넘긴다. AdminAuthBackend.authenticate(admin_auth.py:133)는 세션의 user_id로 매 요청 DB 를 조회해 활성·슈퍼유저가 아니면 세션을 비우고 거부한다(:139~:141). 그래서 강등·비활성화·삭제가 다음 요청부터 반영된다. 비용은 관리 요청마다 PK 조회 1회다.

코드 근거: admin_auth.py · authenticate · test_demoted_user_is_rejected_on_the_next_request

7. 로그아웃 흐름

logout(admin_auth.py:144)은 세션을 비우고 True 를 돌려준다. sqladmin Admin.logout은 True 면 /admin/으로 보내고, 그 요청은 세션이 비어 있으니 로그인 화면으로 간다. 세션이 비면 미들웨어가 쿠키를 지우는 Set-Cookie 를 보낸다(test_logout_clears_the_session).

로그아웃은 이 브라우저의 쿠키 내용을 비우는 것이다. 서버에 세션 저장소·폐기 목록이 없으므로, 로그아웃 전에 복사된 쿠키 값은 Max-Age(8시간)까지 서명상 유효하다. 다만 authenticate가 매 요청 DB 를 보므로 그 계정을 강등·비활성화하면 즉시 끊긴다. 모든 관리 세션을 한 번에 무효로 하려면 SESSION_SECRET_KEY를 교체한다.

코드 근거: admin_auth.py · logout

10. 보안 설계 근거와 위협 모델

위협대응남은 위험
세션 고정로그인 성공 시 session.clear() 후 user_id만 저장—
CSRFSameSite=Strict + Path=/adminsqladmin 폼에 CSRF 토큰이 없다. SameSite 를 지원하지 않는 오래된 브라우저·같은 사이트의 다른 오리진은 막지 못한다
계정 열거실패 사유 미구분(400 메시지 하나), 더미 해시로 응답 시간 균등화—
무차별 대입Redis 고정 창 rate limit(IP·IP+사용자명), 429 + Retry-After고정 창 경계에서 최대 2배 통과(service-hardening R-202). TRUSTED_PROXY_HOPS가 틀리면 전체가 한 IP 로 묶이거나 우회된다
쿠키 탈취HttpOnly·배포 환경 Secure·8시간 만료·매 요청 DB 확인서버측 폐기 목록이 없어 탈취된 쿠키는 만료나 강등·키 교체 전까지 쓸 수 있다
비밀번호 해시 노출app/features/user/admin.py가 상세·폼에서 hashed_password를 제외제외 설정을 지우면 노출 — 지우지 않는다
관리 화면 노출 자체ADMIN_DISABLED=true로 마운트·링크·로그를 모두 없앤다켠 상태에서는 네트워크 경계(프록시·VPN)로 /admin 접근을 더 좁히는 것을 권장

API 에 세션 인증을 섞지 않는 이유: 쿠키는 브라우저가 자동으로 붙이므로 API 가 쿠키를 인정하면 모든 API 쓰기가 CSRF 대상이 되고, 무상태 Bearer 판정(service-hardening ADR-014)과 두 가지 인증 경로가 갈라진다.

설정기본값의미
ADMIN_DISABLEDfalsetrue면 관리 화면 완전 비활성화(마운트·링크·로그 없음)
SESSION_SECRET_KEYplaceholder(배포 검사가 거부)관리 세션 서명 키. 32자 이상, 다른 키와 다른 값. 바꾸면 모든 관리 세션 무효
AUTH_LOGIN_MAX_ATTEMPTS / AUTH_LOGIN_IP_MAX_ATTEMPTS / AUTH_LOGIN_WINDOW_SECONDS5 / 20 / 60API 로그인과 같은 한도(키는 따로)
TRUSTED_PROXY_HOPS0프록시 뒤면 앞단 프록시 단 수. 0 이면 모두 프록시 IP 하나로 묶인다
ENVdevelopmentstaging·production 이면 쿠키 Secure
  • 관리 화면을 쓰지 않으면 ADMIN_DISABLED=true.
  • 쓴다면 scripts/create_superuser.py로 계정을 만들고, SESSION_SECRET_KEY를 실제 키로 바꾸고, HTTPS 뒤에 둔다(배포 환경 쿠키는 Secure).
  • 프록시 뒤면 TRUSTED_PROXY_HOPS를 맞춘다.
  • 예전 ADMIN 설정이 .env·환경 변수에 남아 있지 않은지 확인한다.
증상원인조치
로그인해도 계속 로그인 화면HTTP 로 접속하는데 배포 환경이라 쿠키가 Secure — 브라우저가 저장하지 않음HTTPS 로 접속(프록시 TLS 종료 포함)
맞는 비밀번호인데 400계정이 슈퍼유저가 아니거나 비활성scripts/create_superuser.py --username …로 승격
429창 안 시도 초과. 프록시 뒤인데 TRUSTED_PROXY_HOPS가 0 이면 모든 사용자가 한 IPRetry-After 뒤 재시도, 홉 수 설정
기동 시 “설정 ADMIN 은 ADMIN_DISABLED 로 바뀌었습니다”예전 ADMIN 키가 남아 있음ADMIN 이 false 였다면 ADMIN_DISABLED=true 로 바꾸고, 아니면 그 줄을 지운다
키 교체 뒤 전원 로그아웃SESSION_SECRET_KEY 변경은 기존 서명을 모두 무효로 만든다정상 동작 — 다시 로그인

12. 확장 시 주의

  • 새 관리 뷰: 기능 폴더의 admin.py에 admin_views를 두면 registry 가 등록한다(scripts/new_app.py --with-admin). 인증은 하위 앱 전체에 걸리므로 뷰마다 다시 구현하지 않는다. 자격 증명 컬럼은 상세·폼에서 제외한다.
  • 로그인 화면: app/templates/admin/sqladmin/login.html을 유지한다. 폼 action 은 url_for('admin:login'), 필드 이름은 username·password, 오류는 error 변수(자동 이스케이프)다. Bootstrap 버전을 올리면 실제 파일로 SRI 를 다시 계산하고 tests/test_admin_login.py의 상수를 함께 바꾼다.
  • 세션을 API 에 쓰지 않는다: 앱 전역 SessionMiddleware를 추가하거나 API 의존성이 쿠키를 읽게 하면 test_session_middleware_lives_only_in_the_admin_sub_app·test_admin_session_cookie_does_not_authenticate_the_api가 실패한다. 의도된 가드다.
  • 새 설정 이름 변경: 의미가 뒤집히는 이름 변경은 validate_renamed_settings처럼 잔존 값을 기동 오류로 만든다.
