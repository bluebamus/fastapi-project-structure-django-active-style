9. 요청 밖 작업 — background·Celery

개발·확장의 세부 주제입니다. 목적·책임·운영 및 확장 시 지켜야 할 계약을 설명합니다.

9. 요청 밖 작업 — background·Celery

async with background_db_session() as session:     # 별도 풀, 예외 시 rollback, 끝나면 close
    service = SomeService(session)
    await service.do_write()
    await session.commit()                          # 요청 밖에서는 호출자가 commit
  • Depends 는 요청 밖에서 자동 해석되지 않습니다. 위처럼 컨텍스트를 열고 Service 를 직접 조립합니다.
  • 요청의 세션·Service·Request 를 background 나 Celery payload 로 넘기지 않습니다. JSON 직렬화 가능한 id·값만 넘기고, 작업이 자기 세션을 엽니다.
  • Celery 태스크는 기능 폴더의 tasks.py 에 두고(워커가 registry 로 발견) 코루틴은 run_async() 로 실행합니다. 서비스는 그 기능의 provider 함수(세션을 받는 일반 함수 — 요청용 Depends provider 도 이 함수를 부른다)로 조립합니다 (ARCHITECTURE §11). 재시도·중복·"commit 과 enqueue 사이 실패" 를 테스트합니다.
  • 주기 작업은 같은 tasks.py 에서 beat 스케줄에 직접 등록합니다(중앙 파일을 고치지 않는다). 예: app/features/home/tasks.py 의 접속 로그 보존 정리.

python celery_app.conf.beat_schedule["home.purge_expired_access_logs"] = { "task": "home.purge_expired_access_logs", "schedule": crontab(hour=3, minute=30), # Celery timezone = TIME_ZONE 지역 시각 }

로컬 실행: uv run celery -A app.celery.app:celery_app worker --loglevel=INFO 와 uv run celery -A app.celery.app:celery_app beat --loglevel=INFO(beat 는 배포 전체에서 하나만). 테스트는 스케줄 항목이 등록됐는지와 태스크가 provider 로 조립되는지를 봅니다 (app/features/home/tests/test_access_log_retention.py). 오래 걸리는 삭제는 배치로 나눠 배치마다 커밋합니다(AccessLogRetentionService). - 접속 로그용 access_log_tasks 러너는 넘치면 버리는 비핵심 경로입니다. 결제·발송 같은 중요한 작업을 넣지 않습니다. - async def 안에서 time.sleep·동기 HTTP·큰 파일 처리·무거운 CPU 루프를 돌리면 이벤트 루프가 멈춥니다. blocking I/O 는 asyncio.to_thread, 무겁거나 내구성이 필요한 작업은 Celery 로 보냅니다. - 같은 AsyncSession 으로 asyncio.gather 를 돌리지 않습니다. 한 트랜잭션의 SQL 은 순차 await, 독립 병렬 작업은 작업마다 세션을 엽니다. - 공유 Redis 가 필요하면 core provider get_redis(app/core/redis.py)를 Depends 로 받습니다. 지원 Redis 는 7.0 이상입니다(REDIS_MIN_VERSION, 기동 시 확인). 새 Redis 명령을 쓰면 그 명령의 도입 버전을 app/core/redis.py 의 표와 상수에 반영합니다 — tests/core/test_redis_version.py 가 expire(..., nx=True)·getdel( 사용과 상수를 대조합니다. client 가 없으면 503 이고, 테스트는 app.dependency_overrides[get_redis] 로 가짜를 넣습니다. Redis 연결·시간 초과 오류는 잡지 말고 올립니다 — 전역 핸들러가 503 SERVICE_UNAVAILABLE 로 끝냅니다(fail-closed, ARCHITECTURE 의 Redis 절). 그 밖의 명령 실패(ResponseError 등)의 오류 계약은 쓰는 기능이 정합니다. - auth 경로(가입·로그인·재발급·로그아웃)는 refresh 저장소와 rate limit 때문에 Redis 를 씁니다. 이 경로를 부르는 엔드포인트 테스트는 fakeredis.FakeAsyncRedis() 하나를 만들어 app.dependency_overrides[get_redis] = lambda: fake 로 넣습니다(예: app/features/auth/tests/test_endpoint.py). Redis 를 쓰는 core 클래스는 생성자에 fakeredis 를 넣어 실물 그대로 시험합니다(tests/core/test_refresh_store.py·test_rate_limiter.py). - 사용자를 비활성화·강등·삭제하는 서비스는 /admin 관리 세션도 끊는다 — get_user_service 가 get_admin_session_store(같은 get_redis 사용, ADMIN_DISABLED=true 면 None)를 주입한다. 세션을 끊어야 하는 새 서비스(예: 비밀번호 변경)는 같은 provider 를 받아 revoke_user(user_id) 를 부른다. /admin 흐름 테스트는 tests/test_admin_login.py 의 build_admin_app(SQLite 파일 DB + fakeredis AdminSessionStore)을 쓰고, 상태 변경 요청은 page_token() 으로 꺼낸 CSRF 토큰을 싣는다.
