기능 테스트는 app/features/<name>/tests/, 여러 기능이나 core 계약을 보는 테스트는 최상위 tests/ 에 둡니다. pytest testpaths 가 tests 와 app 을 모두 수집합니다.

의존 방향

features → core → utils
영역 규칙
app/features/<name>/ 비즈니스 코드는 전부 여기. core·utils·config 를 쓰고 다른 기능을 import 하지 않는다. 예외는 auth → user(자격증명을 User 모델이 소유) 하나다.
app/core/ 특정 기능의 Service/Repository 를 직접 알지 않는다. AppRegistry 가 등록을 위해 기능 모듈을 동적 import 하는 것은 예외다. 기능이 core 에 붙어야 하면 등록 훅을 쓴다(예: home 이 set_access_log_sink() 로 접속 로그 저장소를 등록).
app/utils/ 상위 계층을 import 하지 않는다. 누구나 쓸 수 있다.

기능 간 데이터 연결도 import 가 아니라 값으로 합니다. 예: Reply.post_id 는 FK 제약 없는 문자열 참조입니다. 여러 기능이 참여하는 업무 흐름이 생기면 core 로 옮기지 말고 orchestration 경계를 따로 설계합니다. 기능 간 import 금지는 리뷰로 지키는 규칙이고, 테스트가 강제하는 경계는 둘입니다: 접속 로그 미들웨어가 home 을 import 하지 않는다(tests/core/test_access_log_decoupling.py), 발견 단계가 기능의 라우터·모델을 끌어오지 않는다(tests/core/test_import_boundary.py).

2. 앱 자동 등록 (AppRegistry)

app/features/<name>/ 디렉터리를 만드는 것이 곧 앱 등록입니다. 중앙 목록(INSTALLED_APPS)도 앱별 설정 파일도 없습니다. 설계의 뼈대는 발견과 결선의 분리입니다.

app/features/*
      │
AppRegistry.discover()            "어떤 앱이 있는가" — 부작용 0
      ├─ install_hooks()   ──→ 각 앱 apps.py 의 ready()
      ├─ import_models()   ──→ Base.metadata ──→ DEBUG create_all / Alembic
      ├─ install_routers() ──→ app.include_router(<name>_router, prefix="/api")
      ├─ task_modules()    ──→ Celery include (워커 — 각 앱 tasks.py)
      └─ install_admin()   ──→ Admin.add_view(...)   (ADMIN_DISABLED=false 일 때만)

결선 메서드는 마지막 discover() 결과만 쓰고 스스로 다시 스캔하지 않습니다. 목록이 둘이면 런타임과 마이그레이션이 서로 다른 앱을 보게 되고, 그 어긋남은 배포 뒤 "운영에만 테이블이 없다" 로 드러납니다. 요구사항 ID(FR-*·NFR-*·SEC-* 등, 코드 주석이 인용)와 설계 근거는 docs/specs/django-style-app-automation.md에 있습니다.

2.1 규약 — registry 가 찾는 여섯 가지

경로 계약 없으면
<name>/__init__.py 앱 패키지 선언. 부수효과를 두지 않는다 패키지가 아니므로 발견되지 않음
<name>/apps.py ready() — 부팅 시 한 번 실행되는 초기화 훅 훅 없는 앱
<name>/api/routers/router.py <name>_router: APIRouter 라우터 없는 앱
<name>/models/ import 시 ORM 모델이 Base.metadata 에 등록. 패키지와 models.models 모듈을 둘 다 import 한다 모델 없는 앱 (실제 auth)
<name>/admin.py admin_views: list[type] (SQLAdmin ModelView) 관리 화면 없는 앱
<name>/tasks.py Celery 태스크(@celery_app.task(name="<name>.<action>")). 워커 include 에 들어간다 태스크 없는 앱

발견 규칙:

  • app.features 의 직계 하위 패키지만 봅니다(재귀 없음). 이름이 _ 로 시작하면 제외합니다 (__pycache__, 작업 중인 _scratch 등).
  • 순서는 앱 이름 알파벳순으로 고정입니다. 파일시스템 순서와 무관하게 라우트 등록 순서가 같습니다. 앱 사이에 로딩 순서 의존을 만들지 않습니다.
  • 앱 이름은 파이썬 식별자여야 합니다. order-items 같은 디렉터리는 import 할 수 없어 앱이 되지 못합니다.
  • 폴더가 있으면 다음 부팅에 켜집니다. 실험용 코드는 _ 로 시작하는 이름을 쓰거나 app/features 밖에 둡니다.

2.2 오류 정책 — 파일 부재는 선택, 잘못된 계약은 오류

자동 등록은 실패를 조용하게 만듭니다(라우터가 안 붙어도 서버는 뜹니다). 그래서 없는 것과 틀린 것을 구분합니다.

상황 동작
선택 모듈(apps.py·router.py·models·admin.py·tasks.py) 자체가 없다 건너뛴다
선택 모듈 안의 import 가 틀렸다 원래 ModuleNotFoundError 를 그대로 올려 기동 실패
router.py 에 <name>_router 가 없거나 APIRouter 가 아니다 AppContractError 로 기동 실패
admin.py 에 admin_views 가 없다 / list 가 아니다 / ModelView 가 아니다 AppContractError 로 기동 실패
두 앱이 같은 APIRouter 객체나 같은 ModelView 를 내보낸다 AppContractError 로 기동 실패
tasks.py 안의 import 가 틀렸다 발견은 find_spec 으로 존재만 본다(태스크 모듈이 celery_app 을 import 해 순환이 되므로). 워커 기동 시 Celery 가 include 를 import 하며 원래 예외로 실패

판정은 AppModule._import_optional() 이 ModuleNotFoundError.name 이 찾던 그 모듈(또는 상위 패키지) 일 때만 "부재" 로 봅니다. method+path 단위의 라우트 충돌은 registry 가 검사하지 않습니다 — 경로 목록은 tests/test_route_inventory.py 가 고정합니다.

2.3 초기화 훅 — apps.py 의 ready()

# app/features/home/apps.py
from app.features.home.access_log_sink import register_sink


def ready() -> None:
    register_sink()   # core 미들웨어에 자신을 저장소로 등록한다
  • install_hooks() 가 발견 순서대로 호출합니다. main.py 는 FastAPI 인스턴스를 만들기 전에 discover() → install_hooks() → import_models() 를 끝냅니다(훅이 모델 import 보다 먼저).
  • __init__.py 의 import-time 부수효과를 쓰지 않는 이유: "무엇을 import 하면 무슨 일이 일어나는가" 를 코드에서 읽을 수 없고, 테스트가 모듈을 import 하는 것만으로 상태가 바뀌어 결과가 실행 순서에 좌우됩니다.
  • ready() 는 멱등이어야 하고, DB·네트워크 I/O 와 무거운 계산을 하지 않습니다(부팅 시간에 그대로 더해지고 실패 원인이 발견 단계로 숨습니다).
  • Django AppConfig.ready() 와 역할은 같지만, 프레임워크가 보장하는 준비 단계가 아니라 main.py 가 부르는 함수입니다. Alembic 경로는 훅을 호출하지 않습니다.

2.4 결선 지점

호출자 하는 일
main.py 한 AppRegistry 인스턴스로 훅·모델·라우터·Admin 을 모두 결선
migrations/env.py 새 AppRegistry 로 discover() + import_models() (같은 발견 규칙, 훅 없음)
app/celery/app.py 새 AppRegistry 로 discover() + import_models() + task_modules() → include (훅 없음)
app/core/db/models_registry.py import_all_models() — registry 에 위임하는 호환 facade (테스트가 사용)
app/features/admin.py register_admin(app, engine, registry) → create_admin_interface()(Admin 생성 + 로그인 백엔드 AdminAuthBackend 주입, /admin 마운트) → registry.install_admin()(뷰 등록)

register_admin 이 registry 를 인자로 받는 것이 계약입니다. 스스로 발견하면 라우터·모델과 다른 앱 집합을 볼 수 있습니다. Admin 인증 백엔드(app/features/auth/admin_auth.py 의 AdminAuthBackend)는 create_admin_interface() 가 주입합니다(Admin 생성 인자이기 때문 — §10.3). ADMIN_DISABLED=true 면 sqladmin·기능 admin.py·인증 백엔드가 로드조차 되지 않습니다 — 그래서 기능 __init__.py 에서 admin_views 를 재노출하지 않습니다.

2.5 Django 와의 대응 범위

Django 이 프로젝트 판정
앱 registry AppRegistry 가 목록을 한 번 만들어 모든 결선에 제공 대응
AppConfig.ready() 앱 apps.py 의 ready() (install_hooks() 가 호출) 역할만 대응
모델 발견 앱 models import 로 Base.metadata 구성 대응
Admin 등록 앱 admin.py 의 admin_views 자동 수집 대응
startapp python -m scripts.new_app <name> 대응
URLconf <name>_router 를 /api 에 자동 마운트 Django 에 없는 확장
INSTALLED_APPS 디렉터리 존재 자체가 등록 선언 의도적인 차이
settings.py / LOGGING config.py / build_dictconfig() 대응 (앱별 로거 등록은 없음, §5)

Django 호환 계층도 Django 기반도 아닙니다. Django 의 앱 단위 응집도와 registry 개념을 FastAPI 조립 과정에 옮긴 것입니다.

2.6 앱 제거·이름 변경·진단

  • 디렉터리를 지우면 다음 기동에서 라우터·모델·Admin, 그리고 워커의 Celery 태스크(include)에서 빠집니다. 중앙 Celery 패키지는 기능을 import 하지 않으므로 워커도 import 오류 없이 뜹니다. 다만 큐에 이미 들어간 그 앱의 태스크 메시지는 워커가 "등록되지 않은 태스크" 로 버립니다 — 발행을 먼저 멈추고 큐를 비운 뒤 지웁니다. DB 테이블과 데이터는 남습니다 — 보존·이관과 삭제 revision 을 따로 설계합니다.
  • 이름을 바꾸면 공개 URL prefix, <name>_router, import 경로, Celery 태스크 이름 (home.aggregate_access_stats 형태), migration 참조가 함께 바뀝니다.
증상 먼저 볼 것
앱 전체가 안 보인다 직계 하위 패키지인지, __init__.py 가 있는지, 이름이 식별자이고 _ 로 시작하지 않는지
라우터만 없다 api/routers/router.py 경로와 <name>_router 이름
migration 이 비었다 모델이 Base 를 상속하고 models/ 아래에서 import 되는지
Admin 뷰가 없다 ADMIN_DISABLED 값, admin_views 가 ModelView 목록인지
기동 시 ModuleNotFoundError 선택 모듈 내부의 잘못된 import

회귀 가드: tests/test_app_autowiring.py(임시 앱 결선 + 중앙 파일 해시 불변), tests/test_router_registration.py, tests/test_admin_wiring.py(모델을 가진 기능은 자기 admin.py 를 가진다), tests/core/test_registry_*.py(태스크 발견·앱 제거 포함), tests/core/test_celery_app.py(include 출처·Celery 패키지의 기능 import 금지).

3. 기동 순서

main:app import
  ├─ config.py import        설정 객체 생성·검증, validate_env_source() → validate_deployment_safety()
  ├─ app/core/db/session.py   엔진·세션 팩토리 생성 (아직 접속하지 않음)
  ├─ AppRegistry              discover → install_hooks → import_models
  ├─ FastAPI(...)             문서 URL(openapi_url 은 DEBUG 일 때만), lifespan
  ├─ CustomCORSMiddleware(app).configure_cors() → setup_user_info_middleware(app)
  ├─ _register_exception_handlers(app)          4개 글로벌 핸들러
  ├─ registry.install_routers(app)              <name>_router → /api
  ├─ _add_health_and_docs(app)                  /health · /ready · (DEBUG) Scalar /docs
  └─ ADMIN_DISABLED=false → register_admin(app, engine, registry)   (true 면 import·마운트 없음)
ASGI lifespan 진입
  └─ manage_application_resources(app)          Redis ping·버전(≥7.0) → (DEBUG) create_db_tables → yield
  • python main.py 는 조립 후 uvicorn.run("main:app", host=SERVER_HOST, port=SERVER_PORT, reload=DEBUG, log_config=None) 을 호출합니다(uvicorn 로거는 root 의 프로젝트 핸들러로 전파 — §5). uvicorn main:app 으로 띄우면 host/port/reload 는 CLI 옵션이 정합니다(DEBUG=true 가 CLI 에 reload 를 켜 주지 않습니다).
  • --lifespan off 는 Redis 검증과 자원 정리를 건너뛰므로 지원하는 실행 방식이 아닙니다.
  • reload 나 여러 worker 는 프로세스마다 import·lifespan 을 다시 수행합니다. Redis client 와 DB 풀은 worker 마다 따로 있고, Celery 는 별도 프로세스입니다.
  • 엔진 생성은 URL·풀 정책 준비일 뿐입니다. 실제 접속은 DDL, /ready, 세션의 첫 쿼리에서 일어납니다.

4. 설정 (config.py)

4.1 값이 정해지는 방식

  • 각 BaseSettings 클래스가 env_file=".env", extra="ignore" 로 자기 필드를 직접 읽습니다. 우선순위는 프로세스 환경변수 → 현재 작업 디렉터리의 .env → 필드 기본값 입니다.
  • .env 는 작업 디렉터리 기준이라 저장소 루트에서 실행합니다. .env.example 은 복사용일 뿐 자동으로 읽히지 않습니다. .env 가 없어도 기본값으로 뜨지만, 기본 주소의 Redis·MySQL 이 준비됐다는 뜻은 아닙니다.
  • 리스트는 JSON 배열로 씁니다: CORS_ALLOW_ORIGINS=["http://localhost:3000"].
  • get_*_settings() 는 @lru_cache 이고, 파일 끝의 app_settings = get_app_settings() 등이 import 시 전역 인스턴스를 만듭니다. 실행 중 .env 를 바꿔도 반영되지 않습니다. 테스트에서 캐시만 비워도 이미 가져간 전역 참조는 바뀌지 않으므로 새 프로세스나 monkeypatch 로 확인합니다.
  • 타입 오류·validator 위반은 config import 를 실패시켜 lifespan 전에 기동을 막습니다.

5. 로깅

키 표·파일 목록·Django LOGGING 대응표·다중 워커 주의·업그레이드 노트는 README 로깅 이 정본입니다. 여기는 구조만 적습니다.

  • 설정 한 곳. app/utils/logs/config.py 의 build_dictconfig() 가 Django settings.LOGGING 자리이고, 첫 get_logger() 가 configure_logging() 으로 한 번 적용합니다. 핸들러는 root 에만 붙고 loggers 키는 없습니다.
  • 모든 실행 경로가 root 의 핸들러 한 벌을 씁니다. 앱 로거는 root 로 전파합니다. python main.py 는 uvicorn 에 log_config=None 을 넘겨 uvicorn 로거도 root 로 갑니다. uvicorn main:app·fastapi dev 는 앱 import 전에 붙인 자기 핸들러를 configure_logging() 이 걷어 내고(setup.adopt_external_handlers()) root 로 보냅니다. Celery 워커는 after_setup_logger 수신자(app/celery/worker_lifecycle.py)가 프로세스를 celery 로 정하고 root 를 다시 구성합니다 (setup.configure_worker_logging() — --logfile 은 같은 파일 형식의 핸들러로 유지). 태스크 로거(celery.task)는 after_setup_task_logger 에서 자기 핸들러를 걷고 root 로 전파합니다. 그래서 형식·헤더·마스킹·헤더별 레벨이 경로마다 같습니다.
  • 형식. 포매터는 TzFormatter 하나(LOG_CONSOLE_FORMAT·LOG_FILE_FORMAT·LOG_DATE_FORMAT, development 는 .밀리초, staging/production 은 UTC)입니다. 설정 로드 때 샘플 레코드를 렌더해 형식 오류를 막고, 필수 자리표시자 ({asctime}·{levelname}·{appname}·{module}·{classname}·{funcName}·{message})가 빠지면 빠진 목록과 함께 기동 오류입니다. uvicorn 접속 줄은 {message} 가 요청 줄입니다(전용 포매터 없음 — 예전 TzAccessFormatter 는 args 를 풀다 줄을 잃는 위험만 있었다).
  • 헤더(app=). 판별은 filters._app_from_path(pathname, name) 한 함수입니다. 우리 코드는 소스 경로(기능명·core·celery· utils·migrations·app), 설치된 라이브러리는 로거 이름 표(celery/kombu→celery, uvicorn, sqlalchemy, alembic, 그 밖 ext). 새 기능은 등록 없이 기능명 헤더가 붙습니다.
  • 필터 순서(모든 핸들러): ContextFilter(헤더·클래스명) → AppLevelFilter(LOG_APP_LEVELS, 지정 없는 헤더는 LOG_LEVEL) → RedactingFilter → SQLNoiseFilter. root 레벨은 LOG_LEVEL 과 헤더별 레벨 중 최솟값으로 내려 레코드가 필터까지 옵니다. 콘솔·파일 핸들러 레벨(LOG_CONSOLE_LEVEL·LOG_FILE_LEVEL)은 출력처 하한으로 그대로 적용됩니다.
  • 파일. staging/production + LOG_FILE_ENABLED=true 에서만. 이름은 프로세스 종류가 정합니다(LOG_FILES: 웹 app.log·error.log, Celery celery.log·celery-error.log). 종류는 import 때 진입점(argv — celery CLI·python -m celery 면 celery)으로 정하고 Celery 로깅 신호가 한 번 더 확정합니다 — 설정 로드 직후의 기동 초기 줄도 그 프로세스의 파일에 남습니다(integration-e2e F-006). 핸들러 handlers.DailyRotatingFileHandler 가 UTC 자정·하루 안 크기 초과 때 교체하고 교체 시점에 LOG_RETENTION_DAYS 보다 오래된 날짜·분할 파일을 지웁니다. 파일 핸들러는 bounded queue 뒤 listener 스레드가 씁니다 (이벤트 루프가 파일 I/O 로 멈추지 않게). prefork 자식은 listener 스레드를 물려받지 못하므로 worker_process_init 에서 다시 세웁니다 (queue_logging.restart_queue_listener_after_fork(), 같은 프로세스면 아무것도 하지 않음). 한 파일은 한 프로세스가 쓴다는 전제라 여러 워커는 파일 로그를 끄고 stdout 을 수집합니다 — uvicorn 이 spawn 한 워커에서 파일이 켜져 있으면 기동 시 WARNING 한 줄.
  • 콘솔 on/off. LOG_CONSOLE_ENABLED=false 면 root 에 콘솔 핸들러가 없고(모든 경로가 root 를 쓰므로 전부 꺼짐), 파일도 없으면 configure_logging() 이 stderr 에 경고 한 줄을 남깁니다.

마스킹 범위. 메시지·인자·예외 traceback(체인 raise … from 포함)·stack_info 에서 DSN 의 사용자명·비밀번호, password=/token= 형태 값, Bearer <토큰>, 그리고 설정된 비밀값 원문(config.LOG_SECRET_SETTINGS → log_secret_values() → configure_logging() 이 filters.set_secret_values() 로 설치)을 가립니다. 4글자 미만 값은 DSN·user=·username= 에서만 가립니다(일반 단어 보호). 필터가 exc_info 를 traceback 문자열로 미리 렌더해 exc_text 에 고정한 뒤 가리므로 포매터는 가린 본문을 찍고, 예외 타입·파일·줄은 남습니다. 비밀값이 인자 하나 안에 있으면 그 인자만 가려 args 모양을 지키고, 틀과 인자에 걸쳐 있으면(password=%s) 전개한 문자열을 가리고 args 를 비웁니다. 정규식 정본은 filters.redact() 하나입니다. 접속 로그 테이블의 session_id 쿠키·Referer·X-Forwarded-For 원문 저장은 로그 마스킹 대상이 아니며 그대로 유지합니다(사용자 결정 — §7.1).

레벨. 명시값이 DEBUG 기반 기본값보다 우선합니다. 레벨은 "최소 심각도" 입니다.

6. lifespan 과 자원 관리

main.py 의 lifespan 본문은 async with manage_application_resources(app): yield 한 줄이고, 자원 조립은 app/core/resources.py 가 합니다.

app.state.resources = ResourceManager(); app.state.redis = None
register("logging-queue", 5s) · register("db-engines", 10s)
acquire("redis", start=ping+버전 확인, close=aclose, 5s)   ← 정리를 먼저 등록한 뒤 start
register("background-tasks", drain, 5s)
DEBUG=true → create_db_tables()                  ← 30초 guard
yield  (요청 처리 기간)
finally: resources.close(); app.state.redis = None; app.state.resources = None

Redis 는 필수입니다. Redis.from_url(REDIS_URL, socket_connect_timeout=5, socket_timeout=5) 후 ping() 이 실패하면 오류 타입만 ERROR 로 남기고 다시 올려 서버 시작을 멈춥니다. DEBUG 와 무관하고 끄는 설정은 없습니다. 이어서 check_redis_version()(app/core/redis.py)이 INFO server 의 redis_version 을 상수 REDIS_MIN_VERSION(7.0)과 비교해 낮으면 RedisVersionError 로 멈춥니다 — 최소 버전은 코드가 보내는 명령에서 정했습니다(rate limit 의 EXPIRE … NX 7.0 > GETDEL 6.2 > SET … EX 2.6.12). INFO 가 막힌 관리형 Redis(ResponseError)는 WARNING 후 계속하고, 연결 오류는 그대로 올립니다. fakeredis 는 INFO 를 지원하지 않아 테스트·로컬 스모크에서는 경고 경로를 탑니다. 성공해야 app.state.redis 에 client 가 들어갑니다. 기동 이후 상태는 /ready 가 호출마다 PING(2초 상한)으로 확인합니다(§9). 요청 쪽은 core provider get_redis(app/core/redis.py) 하나를 Depends 로 받습니다 — client 가 없으면(기동 전·종료 후) 503 SERVICE_UNAVAILABLE 이고, 테스트는 app.dependency_overrides[get_redis] 로 가짜를 넣습니다. 요청 중 Redis 연결·시간 초과 오류(redis.exceptions.ConnectionError·TimeoutError)는 전역 핸들러 (main._register_exception_handlers 의 redis_unavailable_handler)가 503 SERVICE_UNAVAILABLE 로 끝냅니다 — 요청은 거부하고(fail-closed), traceback 은 그 핸들러가 한 번만 남기며, 정상 응답이라 keep-alive 연결도 유지됩니다. 전역 Exception 핸들러(500)로 흘러가면 Starlette 가 응답 뒤 예외를 다시 올려 서버가 traceback 을 한 번 더 남기고 연결을 끊습니다(integration-e2e F-004). 관리 화면은 자기 세션 미들웨어가 같은 상황을 503 으로 끝냅니다.

개발용 DDL. create_db_tables() 는 writer 엔진에서 Base.metadata.create_all 을 실행합니다. 없는 테이블만 만들고(checkfirst) 컬럼 변경·삭제는 하지 않습니다. 모델 발견은 하지 않으며, metadata 가 비어 있으면 RuntimeError 입니다. MySQL 데이터베이스와 계정 권한은 미리 있어야 합니다. 자동 생성과 Alembic 의 전환 시점은 README 의 스키마 관리 절이 정합니다.

종료. ResourceManager.close() 는 등록 역순(background tasks → Redis → DB engines → logging queue)으로 정리합니다.

  • 멱등입니다. 각 단계의 일반 예외·timeout 은 기록하고 다음 단계로 넘어갑니다.
  • 단계 예산(5/5/10/5초)은 전체 20초 deadline 의 남은 시간으로 줄어들지만, deadline 을 다 쓰면 남은 자원마다 1초 예비분을 주므로 엄격한 20초 상한은 아닙니다.
  • CancelledError 는 잡지 않으므로 정리 중 외부 취소가 오면 뒤 단계가 실행되지 않을 수 있습니다.
  • logging queue 를 멈춘 뒤의 마지막 로그는 파일에 남는다고 보장하지 않습니다. SIGKILL·강제 종료에는 회수 보장이 없습니다.
  • startup 실패도 같은 finally 경로로 정리합니다(아직 등록하지 않은 background drain 은 제외).

미들웨어는 CORS → UserInfo 순서로 등록되며, Starlette 는 나중에 등록한 것을 바깥에 둡니다. 계층별 책임과 트랜잭션 경계(커밋은 쓰기 핸들러 본문이 응답 전에 한 번)는 기능 개발 가이드 §2·§8이 소유합니다.

7.1 접속 로그

core 의 UserInfoMiddleware 가 수집하고, home 앱의 HomeAccessLogSink 가 저장합니다. core 는 AccessLogSink Protocol 과 등록 슬롯(set_access_log_sink())만 알고, 슬롯이 비어 있으면 저장을 건너뜁니다 — home 이 없어도 앱은 동작합니다.

  1. ACCESS_LOG_ENABLED=false 이거나 경로가 ACCESS_LOG_EXCLUDE_PATHS, 확장자가 ACCESS_LOG_EXCLUDE_EXTENSIONS 에 해당하면 그대로 통과시킵니다. 기본 제외: /health·/docs·/redoc·/openapi.json·/favicon.ico, .css .js .ico .png .jpg .jpeg .gif .svg.
  2. call_next() 가 응답을 돌려주면 상태 코드와 response_time_ms 를 붙여 access_log_tasks.spawn() 으로 저장을 제출합니다. 응답은 기다리지 않습니다. 처리되지 않은 예외는 500 으로 기록한 뒤 그대로 다시 던집니다(바깥의 500 핸들러가 응답).
  3. BackgroundTaskRunner 는 동시 256개 상한을 넘으면 새 로그를 버리고 dropped 를 셉니다. 종료 시에는 수락 중단 → 5초 대기 → 남은 태스크 cancel → 취소 완료까지 await 순서로 drain 합니다.
  4. sink 는 background_db_session()(별도 풀)으로 UserAccessLogService 를 조립해 저장하고 명시 commit 합니다. 요청 세션을 넘기지 않습니다. 저장 실패는 로그만 남기고 응답에 영향이 없습니다. 서비스는 저장 직전에 문자열을 모델 컬럼 길이로 자릅니다(String(n) 의 n 을 모델에서 읽는다 — 숫자를 두 번 적지 않는다). 긴 헤더·쿠키 하나 때문에 MySQL strict 모드가 그 요청의 기록을 통째로 거부하지 않게 하려는 것입니다.
분류 필드
네트워크 ip_address, forwarded_for(X-Forwarded-For 원문), real_ip(X-Real-IP 원문)
User-Agent user_agent, os_name, os_version, browser_name, browser_version, device_type, device_brand, device_model, is_bot

ip_address 는 core 의 ClientIPResolver 가 TRUSTED_PROXY_HOPS 로 판정합니다(미들웨어 등록 시 설정에서 한 번 만들어 생성자로 주입). 기본 0 은 전달 헤더를 보지 않고 직접 연결 주소를 씁니다. N 이면 X-Forwarded-For 의 오른쪽에서 N번째 — 각 프록시가 오른쪽 끝에 덧붙이므로 우리 프록시가 붙인 값만 채택하고, 클라이언트가 왼쪽에 써 보낸 값은 보지 않습니다. XFF 가 없으면 X-Real-IP, 목록이 N 개보다 짧거나 값이 IP 가 아니면 직접 연결 주소입니다. query_string 은 ACCESS_LOG_SENSITIVE_QUERY_KEYS(기본 password·token·access_token·refresh_token·secret·api_key·code, 대소문자 무시)의 값을 *** 로 가려 저장합니다. user_id 는 인증 의존성 get_current_principal 이 핸들러 실행 중에 request.state.user_id 로 남긴 값이라, 미들웨어는 응답을 받은 뒤 읽습니다(요청 전에 읽으면 항상 비어 있다). 익명 요청·토큰 검증 실패는 비어 있습니다. 조회 API(/api/v1/home/access-logs*)는 슈퍼유저 전용입니다. user_access_logs 는 ip_address·created_at·device_type· os_name·browser_name·session_id·user_id·country 에 인덱스가 있습니다 — country· country_code·city 컬럼은 선언과 인덱스만 있고 미들웨어가 값을 채우지 않습니다(위 표에 없는 이유).

보존 기간. ACCESS_LOG_RETENTION_DAYS(기본 365, 0 = 삭제 안 함, 음수는 설정 오류)보다 오래된 행은 home 의 AccessLogRetentionService 가 지웁니다 — 기준은 created_at < 지금(UTC) − N일(정확히 N일 전 행은 남는다)이고, 5,000행씩 id 를 골라 지운 뒤 배치마다 커밋합니다(긴 잠금·거대 트랜잭션 방지, 중간 실패는 다음 실행이 이어 지운다). MySQL 이 LIMIT 낀 IN 서브쿼리를 거부하므로 "id 선택 → id 로 DELETE" 두 단계로 두 DB 에서 같은 쿼리를 씁니다. 실행은 Celery beat 가 매일 03:30(TIME_ZONE)에 home.purge_expired_access_logs 를 발행합니다(§11). 원문 필드(session_id·referer·XFF)는 그대로 저장합니다(사용자 결정).

비핵심 로그라서 API 가용성을 로그 완전성보다 우선한 설계입니다. 무손실 감사 로그가 필요하면 내구 큐·재처리·중복 제거를 따로 설계해야 합니다. 개인정보 쪽 한계는 §10.4 를 봅니다.

  • 모든 generator 는 async with 로 세션을 열고 끝나면 닫습니다. 예외로 빠져나가도 close() 가 활성 트랜잭션을 ROLLBACK 한 뒤 예외가 그대로 올라갑니다 — 명시적으로 예외를 잡는 것은 로그를 남기는 get_routed_db_session·get_background_db_session 둘뿐입니다. 성공 시 자동 commit 하지 않습니다.
  • FastAPI Depends 는 요청 안에서만 해석됩니다. 요청 밖에서는 async with background_db_session() as session: 으로 열고 Service 를 직접 조립합니다. Repository 는 세션이 어디서 왔는지 모릅니다.
  • session.py 끝의 옛 별칭은 같은 객체를 가리키는 호환용입니다. 문서와 신규 코드는 정식 이름만 씁니다(대응표: scripts/review_gate.py 의 DEPRECATED_SESSION_ALIASES, 게이트가 문서에서 옛 이름을 거부합니다).
  • 같은 요청에서 같은 Dependency 는 FastAPI 캐시로 재사용되지만, writer/read-only getter 는 서로 다른 callable 이라 같은 세션이 아닙니다.

8.3 읽기/쓰기 라우팅 (DB_ROUTER_ENABLED)

기본값 false — 모든 세션이 writer 엔진 하나에 붙습니다. DB_ROUTER_ENABLED=true 이고 DB_REPLICATION_ENABLED=true + MYSQL_REPLICA_HOSTS 가 있으면 라우팅 세션이 다음을 따릅니다.

  1. ORM flush·Core DML·ORM 잠금 조회(select(...).with_for_update()) → writer
  2. 그 밖의 SELECT → reader (라운드로빈). 한 세션이 고른 reader 는 세션 끝까지 유지(pin)
  3. DB_READ_STICKY_AFTER_WRITE=true(기본) 면 쓰기 뒤 같은 세션의 SELECT → writer
  4. reader 가 없으면 writer
  5. text() Raw SQL 은 1~3 규칙만 따릅니다 — 라우터는 문자열을 해석하지 않으므로 text("SELECT ... FOR UPDATE") 는 reader 로 나갈 수 있습니다. Raw SQL 로 잠금이 필요하면 get_writer_db_session 을 쓰거나 using_writer(session) 으로 직접 고정합니다(§8.2, 개발 가이드 §7)

복제 지연을 허용할 수 없는 읽기는 writer 세션을 쓰거나 using_writer(session) 으로 고정합니다. sticky 는 세션 내부 정책이라 다음 요청의 read-only 세션까지 지연을 없애지 않습니다.

replica 장애 대체(integration-e2e F-005). read-only 세션(get_read_only_db_session)의 읽기가 replica 에서 연결 계열 오류(접속 불가 2002·2003·2005, 끊김 2006·2013·2055, 서버 종료·오프라인 1053·3032, 연결 수 초과 1040, 또는 SQLAlchemy 의 connection_invalidated)로 실패하면, 그 세션을 롤백하고 writer 에 고정한 뒤 같은 구문을 한 번 primary 로 다시 실행하고 WARNING(replica 연결 오류(...) — 이 읽기를 primary 로 한 번 다시 실행합니다, 비밀값 없음)을 남깁니다. 실행 지점은 RoutingSession._execute_internal(execute·scalars·get 이 모두 지난다)입니다. 쓰기·routed 세션, 이미 writer 에 고정된 세션, 문법·제약·잠금 오류, 복제 지연(오류가 아니다), 라우터가 꺼진 구성은 바뀌지 않습니다. /ready 는 replica 를 보지 않습니다(writer·Redis 만).

read-only 집행은 라우터가 꺼져 있어도 적용됩니다. 세션 클래스 이벤트(before_flush, do_orm_execute)가 read-only 세션에서 ORM flush 와, 읽기로 판별되지 않는 구문을 거부합니다. 판별은 괄호 깊이 0 의 단어만 훑습니다 — 읽기 전용 CTE(WITH ... SELECT)는 통과하고, 최상위에 쓰기 키워드가 있는 문장(WITH ... UPDATE·DELETE 포함)·잠금 조회·multi-statement·따옴표나 괄호가 맞지 않아 판별할 수 없는 문장은 거부합니다. session.info 표시는 보안 경계가 아니므로 운영에서는 read-only DB 계정·권한을 최종 방어선으로 둡니다. 회귀 가드: tests/core/test_read_only_guard.py, tests/core/test_db_router.py.

8.4 시각 저장 — UTC·마이크로초

DB 의 시각은 UTC 로 저장합니다. Base.type_annotation_map 이 Mapped[datetime] 을 app/core/models/types.py 의 UTCDateTime 으로 바꿉니다 — aware 값은 UTC 로 변환해 저장하고, naive 값은 ValueError(flush 시 StatementError)로 거부하며, 읽을 때 UTC tzinfo 를 붙입니다. MySQL 컬럼은 DATETIME(6)(마이크로초)입니다. 모델 기본값은 timezone_settings.utc_now() 하나에서 나오고, 응답 JSON 은 ...Z 오프셋을 가집니다. TIME_ZONE 은 저장값의 의미를 바꾸지 않습니다 — 로그 표시·리포트 영업일·Celery beat 표시에만 쓰입니다. 리포트는 지역 날짜 범위를 UTC 반열린 구간으로 바꿔 조회하고 DATE(CONVERT_TZ(created_at, '+00:00', <오프셋>)) 로 묶습니다(쿼리당 고정 오프셋 — DST 지역은 행별 변환이 필요합니다). 회귀 가드: tests/core/test_utc_datetime.py, MySQL 은 tests/integration/test_mysql_utc_datetime.py.

  • OAuth2 password flow + JWT access/refresh(PyJWT). 자격증명은 User.hashed_password 에 있고 auth 는 인증 로직만 갖습니다(모델 없는 앱).
  • claims: sub, type, iat, nbf, exp, jti, iss, aud + access 는 username·su(발급 시점의 슈퍼유저 여부, bool 이 아니면 거부), refresh 는 fam(로그인 세션 = family id). 검증은 허용 알고리즘 목록(설정 하나)·audience·issuer·leeway·필수 claim 을 모두 지정하고, type 이 다르면 거부합니다. access 와 refresh 는 서로 다른 키로 서명합니다. 실패 이유와 관계없이 InvalidTokenException(401 AUTH_INVALID_TOKEN, core) 하나로 응답합니다.
  • refresh 회전·재사용 탐지: 발급할 때 auth:rt:{jti} → {fam, sub}(TTL = refresh 만료)와 auth:user:{sub}:fams 를 기록합니다. /refresh 는 jti 를 GETDEL 로 소비하고 같은 family 로 새 쌍을 발급합니다. 소비된 jti 가 다시 오면 재사용으로 보고 family 를 폐기(auth:fam:{fam}:revoked)한 뒤 401 — 그 사이 정상 회전으로 받은 토큰도 함께 죽습니다. 사용자가 없거나 비활성이어도 family 를 폐기합니다. /logout 은 family 를 폐기하고 이미 쓴 토큰이어도 204 입니다. revoke_user(sub) 는 사용자의 모든 family 를 폐기합니다.
  • rate limit: 라우트 의존성 login_rate_limit(IP, IP+소문자 사용자명)·register_rate_limit(IP)이 핸들러 전에 셉니다. 초과는 TooManyRequestsException(429, Retry-After) — AppException 의 headers 를 전역 핸들러가 응답에 싣습니다. 로그인 성공 시 IP+사용자명 카운터를 지웁니다. IP 는 접속 로그와 같은 ClientIPResolver(TRUSTED_PROXY_HOPS)로 판정합니다.
  • 해시 이전: 새 해시는 Argon2(pwdlib). $2 로 시작하는 옛 bcrypt 해시는 옛 규칙(UTF-8 72바이트 절단)으로 검증하고, 맞으면 Argon2 해시로 바꿔 저장합니다 — /login 핸들러가 커밋합니다.
  • get_current_user(auth)는 get_current_principal 이 검증한 주체로 read-only 세션에서 활성 사용자를 읽습니다 — 엔티티가 필요한 /me 만 씁니다. 이 조회는 replica 가 아니라 primary 로 갑니다(using_writer, e2e-policy-2 결정 5) — 복제 지연 때 유효한 토큰이 401 이 되지 않고, 비활성화·삭제가 바로 반영됩니다. 나머지 read-only 조회의 라우팅은 그대로입니다. 이 객체를 쓰기 세션에서 직접 수정하지 말고, 쓰기 세션으로 다시 조회합니다.
  • 상수 시간 인증: 사용자가 없거나 해시가 없어도 Argon2 더미 해시로 검증을 수행해 응답 시간으로 사용자명 존재를 알아내기 어렵게 합니다(네트워크 변동까지 없애지는 못합니다).
  • 논블로킹 해싱: 해시·검증은 asyncio.to_thread 로 이벤트 루프 밖에서 돕니다.

10.2 인가 — 인증 주체 · 슈퍼유저 · 소유권 (app/core/security/)

권한은 슈퍼유저/일반 2단계입니다(users.is_superuser, 기본 false). 판정 부품은 core 에 하나씩 있고, 기능은 core 만 의존합니다.

get_current_principal / CurrentPrincipal dependencies.py Bearer access 토큰 → TokenService.decode → Principal. DB 조회 없음. 성공 시 request.state.user_id 를 남긴다(접속 로그가 응답 뒤에 읽는다). 실패 401

  • 무상태 판정: 보호 라우트는 토큰만 봅니다. 비활성화·강등은 refresh family 폐기(revoke_user)와 짧은 access 만료(기본 15분)로 반영됩니다 — 이미 발급된 access 토큰은 만료까지 남습니다.
  • 소유권은 서비스가 판정합니다. blog·sns·reply·user 서비스는 생성자로 OwnershipPolicy 를 받고, 수정·삭제 메서드가 principal 을 인자로 받아 존재 확인(404) 뒤 판정합니다(403). user 단건 조회· 수정은 사용자 자신이 소유자이며, 존재 확인 전에 판정해 남의 id 로 존재 여부를 떠볼 수 없습니다.
  • 작성자는 서버가 채웁니다. 생성 시 author_id = principal.id, author = principal.username. 요청 본문의 author 는 무시되고 Update 스키마에는 없습니다. author_id 는 FK 없는 String(36)(인덱스) — 사용자를 지워도 글은 남습니다.
  • user 의 특권 필드: is_active·is_superuser 는 슈퍼유저만 바꿉니다(본인이면 403 USER_PRIVILEGED_FIELD). 비활성화·강등·삭제는 RefreshTokenStore.revoke_user 로 그 사용자의 모든 refresh family 를 폐기합니다. 생성(POST /users)은 슈퍼유저 전용이고 비밀번호가 필수입니다.
  • 첫 슈퍼유저: API 에는 경로가 없습니다(가입은 항상 일반 사용자). scripts/create_superuser.py 가 background_db_session + core get_password_hasher + UserRepository 로 만들거나 승격합니다 (README "첫 관리자 만들기").
  • 접근 수준의 정본은 뷰 선언이고, 기본 정책은 거부입니다. 선언하지 않은 뷰는 열린 채 배포되는 대신 서버가 뜨지 않습니다. 데코레이터 선언만으로는 "선언을 잊은 뷰" 를 막을 수 없어 기동 검사를 둡니다. 함수를 감싸는 @login_required 식 데코레이터는 쓰지 않습니다 — FastAPI 는 뷰 시그니처로 주입·검증· OpenAPI 를 만들기 때문에 감싸면 셋이 함께 깨집니다. 핸들러 인자 CurrentPrincipal·SuperuserPrincipal 은 선언으로 인정되므로 같은 수준을 데코레이터에 중복으로 적지 않습니다. 예시 정책이 의도대로인지는 tests/test_authorization.py 의 EXPECTED 표(README 권한 표와 같은 내용)가 가드의 판정·OpenAPI security 표시와 대조해 고정합니다. 소유자 판정은 선언이 아니라 서비스 동작이라 같은 파일의 실요청 테스트가 맡습니다.

10.3 SQLAdmin

  • /admin 은 활성 슈퍼유저 로그인이 필요합니다(admin-login ADR-002). create_admin_interface() 가 AdminAuthBackend(app/features/auth/admin_auth.py)를 주입합니다. 로그인은 API 로그인과 같은 verify_credentials(Argon2·bcrypt 재해시·비활성 거부)를 쓰고, 슈퍼유저가 아니면 실패입니다. 실패 사유는 구분하지 않습니다(400). 시도 수는 API 와 같은 AUTH_LOGIN_* 한도로 키를 따로 셉니다 (admin:rl:, 초과 시 로그인 화면을 429 + Retry-After 로).
  • 세션은 /admin 하위 앱에만 붙은 Redis 서버 세션입니다(app/core/security/admin_session.py — 저장소 AdminSessionStore, ASGI 미들웨어 RedisSessionMiddleware). 쿠키 admin_session(Path=/admin, SameSite=Strict, HttpOnly, Max-Age=절대 만료, staging/production 은 Secure)에는 secrets.token_urlsafe(32) 세션 ID 만 있고, 내용 {"data", "user_id", "created_at"} 은 Redis admin:sess:{HMAC-SHA256(SESSION_SECRET_KEY, ID)} 에 있습니다(TTL = min(미사용, 절대 만료까지 남은 시간), 요청마다 갱신). 사용자별 인덱스 admin:user_sessions:{user_id} 로 한 사용자의 세션을 한 번에 지웁니다. 로그인 성공은 세션을 비우고 사용자 id·새 CSRF 토큰을 넣은 뒤 rotate_session 으로 세션 ID 를 새로 발급하고 이전 키를 지웁니다. 로그아웃·authenticate 거부는 키를 지우고, 사용자 서비스의 비활성화·강등·삭제는 refresh 폐기와 같은 지점에서 AdminSessionStore.revoke_user 를 부릅니다(get_user_service 가 주입, ADMIN_DISABLED=true 면 None). 관리 화면에서 직접 고친 경우는 UserAdmin 의 커밋 전 훅 on_model_change(비활성화·슈퍼유저 해제·비밀번호 해시 변경일 때만, 변경 전후 비교)·on_model_delete 가 UserService 와 같은 판정 revocation_for·폐기 revoke_user_access 를 부릅니다(규칙 한 곳 — 관리 화면 경로 = API 경로). 비활성화·슈퍼유저 해제·비밀번호 해시 변경·삭제면 관리 세션과 refresh 를 모두 끊습니다. Redis 폐기가 실패하면 예외로 커밋이 막혀 DB 변경이 남지 않습니다(fail-closed). 자기 강등은 지금 세션도 끊습니다. 매 요청 DB 확인도 유지합니다(이중 방어). Redis 오류는 503 입니다(fail-closed) — 쿠키 없는 첫 요청처럼 응답 직전에 새 세션을 저장하다 실패해도 같습니다.
  • 세션은 관리 화면 전용입니다. 메인 앱에는 세션 미들웨어가 없고, API 보호 경로는 Bearer 토큰만 봅니다 — 관리 세션 쿠키로 API 를 호출해도 401 입니다. 회귀 가드: tests/test_admin_login.py 의 세션 범위 테스트.
  • 로그인 화면은 app/templates/admin/sqladmin/login.html(Bootstrap 5.3.8 CSS, SRI 고정, JS 없음)이 sqladmin 기본 화면을 덮어씁니다(templates_dir 의 FileSystemLoader 가 먼저 찾는다).
  • CSRF(synchronizer token, 세션에 하나): 템플릿 전역 함수 csrf_token(request)(AdminAuthBackend.csrf_token) 가 세션에 secrets.token_urlsafe(32) 토큰을 둡니다. 로그인 폼은 hidden 필드로 싣고 login() 이 레이트 리밋·자격 확인 전에 csrf_valid(bytes hmac.compare_digest)로 비교합니다. 로그인 이후의 모든 POST·PUT·PATCH·DELETE(생성·수정·삭제·일괄 삭제·가져오기·로그아웃)는 하위 앱의 AdminCsrfMiddleware 가 헤더 X-CSRF-Token 또는 폼 필드 csrf_token(본문 버퍼링 후 receive 재생)을 같은 함수로 비교해 403 으로 막습니다(로그인 POST 는 건너뜀 — 검사는 한 번). 버퍼링하는 폼 본문은 10 MiB 까지입니다 — Content-Length 로 먼저, 없거나 거짓이면 읽는 도중 누적 크기로 판정해 넘으면 413, 1 MiB 를 넘는 필드(starlette 폼 파서 기본 상한)나 깨진 폼은 400 입니다(e2e-policy-2 결정 7, 상한은 admin_auth.py 의 상수). 토큰은 app/templates/admin/sqladmin/base.html(원본 sqladmin_original/base.html 상속, head_tail 블록만 추가)의 meta 와 인라인 스크립트가 폼 제출·XHR·fetch 에 붙입니다. 로그아웃은 _make_logout_post_only 가 POST 전용으로 바꾸고(GET 405) 스크립트가 링크를 POST 폼으로 바꿉니다. sqladmin 원본이 어긋나면 test_packaged_templates_still_fit_the_base_override 가 실패합니다.
  • 목록 날짜 필터: created_at 이 있는 모든 뷰가 core 의 LocalDateFilter(app/core/admin_filters.py)를 씁니다. 입력 YYYY-MM-DD 를 TIME_ZONE 의 [자정, 다음 자정) 으로 보고 UTC aware 범위로 바꿔 질의합니다 (같은 날 / 이후(포함) / 이전(미포함) / 기간 YYYY-MM-DD~YYYY-MM-DD — 시작일 00:00 ≤ t < 종료일 다음날 00:00, 한쪽만 있으면 열린 구간, 역순·형식 오류는 필터 미적용). 전용 템플릿 sqladmin/filters/local_date_filter.html(sqladmin 이 필터 객체의 template 을 include 한다)이 날짜 입력 두 개를 한 값으로 합쳐 보내고, 빠른 선택(오늘·최근 7일·30일)은 기간 링크입니다. 기본 OperationColumnFilter 는 UTCDateTime 을 날짜로 보지 못해 문자열을 바인딩하고 500 이 났습니다. 잘못된 입력은 필터 없이 목록을 보여 주고 WARNING 을 남깁니다.
  • ADMIN_DISABLED=true 면 /admin 이 아예 없습니다(404). sqladmin·관리 세션 미들웨어·인증 백엔드를 만들지 않고 OpenAPI·/docs·오류 응답·헤더·기동 로그 어디에도 관리 경로가 나오지 않습니다 (tests/test_admin_disabled.py). 관리 화면을 쓰지 않는 배포는 끕니다.
  • User.hashed_password 는 목록·상세·폼·내보내기 어디에도 나오지 않고, User 는 Admin 에서 생성할 수 없습니다(비밀번호 없는 계정 방지). 구조 증거: tests/core/test_admin_views.py.
  • 설계·흐름도·위협 모델·운영 절차 전체: admin 인증 안내서.

11. Celery (요청 밖 작업)

  • app/celery/app.py 의 celery_app 은 REDIS_URL 을 broker/backend 로 씁니다. include 는 API 와 같은 AppRegistry 발견 결과(task_modules())로 만들고, 같은 경로로 모델도 등록합니다 (import_models() — 태스크가 쓰는 모델의 relationship 이 다른 앱을 가리켜도 매퍼가 구성된다). app/celery/ 는 기능을 import 하지 않습니다(tests/core/test_celery_app.py 의 AST 계약).
  • 태스크는 기능 폴더의 선택 모듈 app/features/<name>/tasks.py 에 @celery_app.task(name="<app>.<action>") 로 정의합니다(예: home.aggregate_access_stats). 기능별 worker/ 는 두지 않습니다.
  • 앱을 지우면 그 앱의 태스크도 include 에서 빠집니다. 고칠 중앙 목록이 없고 워커는 그대로 뜹니다(큐에 남은 메시지는 §2.6).
  • include 모듈의 import 는 CI 가 검사합니다. tests/core/test_celery_app.py 의 test_celery_include_modules_import_and_register_their_tasks 가 워커 기동 때처럼 include 를 import 하고 각 모듈이 태스크를 등록했는지 본다 — tasks.py 의 import 오류가 워커 기동이 아니라 CI 에서 드러난다.
  • 태스크 본문의 서비스 조립은 그 기능의 provider 함수(세션을 받는 일반 함수, 예: build_user_access_log_service(session))를 재사용합니다. 요청용 Depends provider 도 같은 함수를 부르므로 조립 경로가 하나입니다.
  • 동기 태스크 안에서 코루틴은 app/celery/task.py 의 run_async(coro) 로 실행합니다. 워커 프로세스마다 영속 이벤트 루프 하나를 재사용해, 닫힌 루프에 묶인 async 풀 연결 문제를 피합니다(prefork 순차 실행 전제 — 다른 pool 을 쓰면 재검증).
  • worker_lifecycle.register_worker_signals() 가 prefork 자식 초기화에서 상속된 sync 풀을 폐기(dispose(close=False))하고 루프를 새로 만들며, 종료 시 루프를 닫습니다. async DB dispose 까지 하지는 않습니다.
  • API 기동은 worker/beat 를 띄우지 않고, API lifespan 이 워커 자원을 정리하지도 않습니다.
  • enable_utc=True 입니다 — ETA·만료·결과 시각은 UTC 로 다루고, timezone(TIME_ZONE)은 beat crontab 해석·표시에만 쓰입니다.
  • beat 스케줄은 태스크를 가진 기능이 등록합니다. 중앙 앱은 beat_schedule={} 만 두고, 기능의 tasks.py 가 import 될 때 celery_app.conf.beat_schedule["<app>.<action>"] = {...} 로 자기 항목을 넣습니다(중앙 목록이 기능을 import 하지 않는다 — include 와 같은 철학). beat 도 워커처럼 시작 시 include 를 import 하므로 이 등록이 보입니다. 현재 항목: home.purge_expired_access_logs 매일 03:30(crontab(hour=3, minute=30), TIME_ZONE 기준). 실행: celery -A app.celery.app:celery_app beat(배포 전체에서 하나만).
  • 태스크에는 요청 세션·Service·Request 를 넘기지 않고 JSON 직렬화 가능한 id·값만 넘깁니다. 태스크가 background_db_session() 을 열고 재시도·중복 정책을 스스로 정합니다.

migrations/env.py 는 런타임과 같은 발견 규칙으로 모델을 모읍니다. 새 앱을 추가해도 이 파일은 고치지 않습니다. FastAPI lifespan 에 들어가지 않으므로 Redis ping 도 하지 않습니다.

  • URL 우선순위(DatabaseSettings.ALEMBIC_URL, URL 객체): ALEMBIC_DATABASE_URL 설정값(make_url) → primary URL 의 드라이버만 mysql+pymysql 로 바꾼 값. env.py 는 환경변수를 직접 읽지 않습니다.
  • DSN 은 문자열로 이어 붙이지 않고 URL.create(...) 로 만듭니다 — 비밀번호의 @ / : # 는 렌더링 때 인코딩되고, % 는 ConfigParser 보간을 피하려고 %% 로 넘깁니다. 회귀 가드: tests/core/test_dsn_urls.py.
  • revision 체인: f4adf0ae24ea(baseline) → b2f1a9c0d3e4(user 비밀번호) → c3d5e7a91b02(catalog_products) → d4e6f8b12c34(sales_orders) → e5a7c9d1f3b5(시각 컬럼 UTC·DATETIME(6)) → a7c3e9f1b2d4(슈퍼유저·작성자 id 컬럼, head).
  • e5a7c9d1f3b5 는 MySQL 에서만 동작합니다(SQLite no-op). 기존 값을 CONVERT_TZ(col, '+09:00', '+00:00') 로 옮기므로 기존 데이터가 +09:00(Asia/Seoul 벽시계)으로 저장됐다는 가정입니다 — 적용 전에 백업하고, 다른 시간대로 운영하던 DB 는 적용 전에 리비전의 _LOCAL_OFFSET 상수를 그 오프셋으로 바꿔야 합니다(README 운영 배포 확인 7). downgrade 는 역변환 후 DATETIME 으로 좁힙니다(소수 초 반올림).
  • autogenerate 는 UTCDateTime 을 sa.DateTime().with_variant(mysql.DATETIME(fsp=6), "mysql") 로 적습니다 (env.py 의 render_item=render_alembic_type) — 리비전이 앱 클래스를 import 하지 않습니다.
  • 서버 기동은 upgrade 를 하지 않습니다. 운영은 트래픽 전환 전에 alembic upgrade head 를 적용합니다.
  • 회귀 가드: tests/core/test_migration_chain.py(빈 DB upgrade head 결과 = ORM metadata), tests/core/test_alembic_metadata.py, 게이트 structure 그룹(alembic heads 단일 head).
