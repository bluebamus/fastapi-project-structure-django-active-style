5. 로깅

키 표·파일 목록·Django LOGGING 대응표·다중 워커 주의·업그레이드 노트는 README 로깅 이 정본입니다. 여기는 구조만 적습니다.

  • 설정 한 곳. app/utils/logs/config.py 의 build_dictconfig() 가 Django settings.LOGGING 자리이고, 첫 get_logger() 가 configure_logging() 으로 한 번 적용합니다. 핸들러는 root 에만 붙고 loggers 키는 없습니다.
  • 모든 실행 경로가 root 의 핸들러 한 벌을 씁니다. 앱 로거는 root 로 전파합니다. python main.py 는 uvicorn 에 log_config=None 을 넘겨 uvicorn 로거도 root 로 갑니다. uvicorn main:app·fastapi dev 는 앱 import 전에 붙인 자기 핸들러를 configure_logging() 이 걷어 내고(setup.adopt_external_handlers()) root 로 보냅니다. Celery 워커는 after_setup_logger 수신자(app/celery/worker_lifecycle.py)가 프로세스를 celery 로 정하고 root 를 다시 구성합니다 (setup.configure_worker_logging() — --logfile 은 같은 파일 형식의 핸들러로 유지). 태스크 로거(celery.task)는 after_setup_task_logger 에서 자기 핸들러를 걷고 root 로 전파합니다. 그래서 형식·헤더·마스킹·헤더별 레벨이 경로마다 같습니다.
  • 형식. 포매터는 TzFormatter 하나(LOG_CONSOLE_FORMAT·LOG_FILE_FORMAT·LOG_DATE_FORMAT, development 는 .밀리초, staging/production 은 UTC)입니다. 설정 로드 때 샘플 레코드를 렌더해 형식 오류를 막고, 필수 자리표시자 ({asctime}·{levelname}·{appname}·{module}·{classname}·{funcName}·{message})가 빠지면 빠진 목록과 함께 기동 오류입니다. uvicorn 접속 줄은 {message} 가 요청 줄입니다(전용 포매터 없음 — 예전 TzAccessFormatter 는 args 를 풀다 줄을 잃는 위험만 있었다).
  • 헤더(app=). 판별은 filters._app_from_path(pathname, name) 한 함수입니다. 우리 코드는 소스 경로(기능명·core·celery· utils·migrations·app), 설치된 라이브러리는 로거 이름 표(celery/kombu→celery, uvicorn, sqlalchemy, alembic, 그 밖 ext). 새 기능은 등록 없이 기능명 헤더가 붙습니다.
  • 필터 순서(모든 핸들러): ContextFilter(헤더·클래스명) → AppLevelFilter(LOG_APP_LEVELS, 지정 없는 헤더는 LOG_LEVEL) → RedactingFilter → SQLNoiseFilter. root 레벨은 LOG_LEVEL 과 헤더별 레벨 중 최솟값으로 내려 레코드가 필터까지 옵니다. 콘솔·파일 핸들러 레벨(LOG_CONSOLE_LEVEL·LOG_FILE_LEVEL)은 출력처 하한으로 그대로 적용됩니다.
  • 파일. staging/production + LOG_FILE_ENABLED=true 에서만. 이름은 프로세스 종류가 정합니다(LOG_FILES: 웹 app.log·error.log, Celery celery.log·celery-error.log). 종류는 import 때 진입점(argv — celery CLI·python -m celery 면 celery)으로 정하고 Celery 로깅 신호가 한 번 더 확정합니다 — 설정 로드 직후의 기동 초기 줄도 그 프로세스의 파일에 남습니다(integration-e2e F-006). 핸들러 handlers.DailyRotatingFileHandler 가 UTC 자정·하루 안 크기 초과 때 교체하고 교체 시점에 LOG_RETENTION_DAYS 보다 오래된 날짜·분할 파일을 지웁니다. 파일 핸들러는 bounded queue 뒤 listener 스레드가 씁니다 (이벤트 루프가 파일 I/O 로 멈추지 않게). prefork 자식은 listener 스레드를 물려받지 못하므로 worker_process_init 에서 다시 세웁니다 (queue_logging.restart_queue_listener_after_fork(), 같은 프로세스면 아무것도 하지 않음). 한 파일은 한 프로세스가 쓴다는 전제라 여러 워커는 파일 로그를 끄고 stdout 을 수집합니다 — uvicorn 이 spawn 한 워커에서 파일이 켜져 있으면 기동 시 WARNING 한 줄.
  • 콘솔 on/off. LOG_CONSOLE_ENABLED=false 면 root 에 콘솔 핸들러가 없고(모든 경로가 root 를 쓰므로 전부 꺼짐), 파일도 없으면 configure_logging() 이 stderr 에 경고 한 줄을 남깁니다.

마스킹 범위. 메시지·인자·예외 traceback(체인 raise … from 포함)·stack_info 에서 DSN 의 사용자명·비밀번호, password=/token= 형태 값, Bearer <토큰>, 그리고 설정된 비밀값 원문(config.LOG_SECRET_SETTINGS → log_secret_values() → configure_logging() 이 filters.set_secret_values() 로 설치)을 가립니다. 4글자 미만 값은 DSN·user=·username= 에서만 가립니다(일반 단어 보호). 필터가 exc_info 를 traceback 문자열로 미리 렌더해 exc_text 에 고정한 뒤 가리므로 포매터는 가린 본문을 찍고, 예외 타입·파일·줄은 남습니다. 비밀값이 인자 하나 안에 있으면 그 인자만 가려 args 모양을 지키고, 틀과 인자에 걸쳐 있으면(password=%s) 전개한 문자열을 가리고 args 를 비웁니다. 정규식 정본은 filters.redact() 하나입니다. 접속 로그 테이블의 session_id 쿠키·Referer·X-Forwarded-For 원문 저장은 로그 마스킹 대상이 아니며 그대로 유지합니다(사용자 결정 — §7.1).

레벨. 명시값이 DEBUG 기반 기본값보다 우선합니다. 레벨은 "최소 심각도" 입니다.

DEBUG LOG_LEVEL / LOG_CONSOLE_LEVEL 콘솔에 나오는 것
false 미설정 / 미설정 INFO 이상
true 미설정 / 미설정 DEBUG 이상
false DEBUG / DEBUG DEBUG 이상 (앱은 여전히 DEBUG=false 동작)
무관 INFO / DEBUG INFO 이상 — 헤더별 레벨(LOG_APP_LEVELS)로 낮춘 헤더만 DEBUG
무관 DEBUG / INFO INFO 이상

기동 로그의 (DEBUG=%s) 는 표시값일 뿐 출력 조건이 아닙니다. 기동 INFO 가 안 보이면 LOG_LEVEL·LOG_CONSOLE_LEVEL· LOG_APP_LEVELS 를 먼저 봅니다.

from app.utils.logs import get_logger

logger = get_logger(__name__)          # 헤더 app= 은 이름이 아니라 소스 경로가 정한다
logger.info("상품 생성: %s", product.id)
logger.exception("저장 실패")            # 스택 트레이스 포함
