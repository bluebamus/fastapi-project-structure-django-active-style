10. 인증과 보안 경계

10.1 JWT (auth 앱, app/core/security/)

역할마다 클래스 하나이고, 협력 객체는 생성자로 받습니다. 여러 기능이 함께 쓰는 provider (해시기·토큰·refresh 저장소·소유권·인증 주체)는 core app/core/security/dependencies.py 에, auth 전용 provider(rate limit·AuthService)는 auth 의 dependencies/auth_dependencies.py 에 있습니다 — user 기능도 해시기·refresh 저장소를 쓰므로 auth 를 import 하지 않도록 core 로 올렸습니다(기능끼리 import 금지).

클래스 위치 역할 provider
PasswordHasher app/core/security/password_hasher.py Argon2 해시, 옛 bcrypt 해시 검증·재해시 (가입·사용자 생성·운영 스크립트 공유) get_password_hasher(core, 프로세스 단일)
TokenService app/core/security/tokens.py JWT 발급·검증 — 검증 규칙의 유일한 정의 지점 get_token_service(core)
RefreshTokenStore app/core/security/refresh_store.py refresh jti 기록·소비(GETDEL)·family 폐기 get_refresh_token_store(core, get_redis)
RateLimiter app/core/security/rate_limiter.py Redis 고정 창(INCR + 첫 hit EXPIRE NX, MULTI) get_rate_limiter(get_redis)
AuthService app/features/auth/services/auth_service.py register · authenticate · issue_tokens · rotate · logout get_auth_service
  • OAuth2 password flow + JWT access/refresh(PyJWT). 자격증명은 User.hashed_password 에 있고 auth 는 인증 로직만 갖습니다(모델 없는 앱).
  • claims: sub, type, iat, nbf, exp, jti, iss, aud + access 는 username·su(발급 시점의 슈퍼유저 여부, bool 이 아니면 거부), refresh 는 fam(로그인 세션 = family id). 검증은 허용 알고리즘 목록(설정 하나)·audience·issuer·leeway·필수 claim 을 모두 지정하고, type 이 다르면 거부합니다. access 와 refresh 는 서로 다른 키로 서명합니다. 실패 이유와 관계없이 InvalidTokenException(401 AUTH_INVALID_TOKEN, core) 하나로 응답합니다.
  • refresh 회전·재사용 탐지: 발급할 때 auth:rt:{jti} → {fam, sub}(TTL = refresh 만료)와 auth:user:{sub}:fams 를 기록합니다. /refresh 는 jti 를 GETDEL 로 소비하고 같은 family 로 새 쌍을 발급합니다. 소비된 jti 가 다시 오면 재사용으로 보고 family 를 폐기(auth:fam:{fam}:revoked)한 뒤 401 — 그 사이 정상 회전으로 받은 토큰도 함께 죽습니다. 사용자가 없거나 비활성이어도 family 를 폐기합니다. /logout 은 family 를 폐기하고 이미 쓴 토큰이어도 204 입니다. revoke_user(sub) 는 사용자의 모든 family 를 폐기합니다.
  • rate limit: 라우트 의존성 login_rate_limit(IP, IP+소문자 사용자명)·register_rate_limit(IP)이 핸들러 전에 셉니다. 초과는 TooManyRequestsException(429, Retry-After) — AppException 의 headers 를 전역 핸들러가 응답에 싣습니다. 로그인 성공 시 IP+사용자명 카운터를 지웁니다. IP 는 접속 로그와 같은 ClientIPResolver(TRUSTED_PROXY_HOPS)로 판정합니다.
  • 해시 이전: 새 해시는 Argon2(pwdlib). $2 로 시작하는 옛 bcrypt 해시는 옛 규칙(UTF-8 72바이트 절단)으로 검증하고, 맞으면 Argon2 해시로 바꿔 저장합니다 — /login 핸들러가 커밋합니다.
  • get_current_user(auth)는 get_current_principal 이 검증한 주체로 read-only 세션에서 활성 사용자를 읽습니다 — 엔티티가 필요한 /me 만 씁니다. 이 조회는 replica 가 아니라 primary 로 갑니다(using_writer, e2e-policy-2 결정 5) — 복제 지연 때 유효한 토큰이 401 이 되지 않고, 비활성화·삭제가 바로 반영됩니다. 나머지 read-only 조회의 라우팅은 그대로입니다. 이 객체를 쓰기 세션에서 직접 수정하지 말고, 쓰기 세션으로 다시 조회합니다.
  • 상수 시간 인증: 사용자가 없거나 해시가 없어도 Argon2 더미 해시로 검증을 수행해 응답 시간으로 사용자명 존재를 알아내기 어렵게 합니다(네트워크 변동까지 없애지는 못합니다).
  • 논블로킹 해싱: 해시·검증은 asyncio.to_thread 로 이벤트 루프 밖에서 돕니다.

10.2 인가 — 인증 주체 · 슈퍼유저 · 소유권 (app/core/security/)

권한은 슈퍼유저/일반 2단계입니다(users.is_superuser, 기본 false). 판정 부품은 core 에 하나씩 있고, 기능은 core 만 의존합니다.

부품 위치 역할
Principal authorization.py 검증된 access 토큰의 주체(id, username, is_superuser) — frozen dataclass
get_current_principal / CurrentPrincipal dependencies.py Bearer access 토큰 → TokenService.decode → Principal. DB 조회 없음. 성공 시 request.state.user_id 를 남긴다(접속 로그가 응답 뒤에 읽는다). 실패 401
require_superuser / SuperuserPrincipal dependencies.py 주체가 슈퍼유저가 아니면 403 FORBIDDEN
OwnershipPolicy.ensure_can_modify(owner_id, principal) authorization.py 소유자 또는 슈퍼유저만 통과, 아니면 403. owner_id 가 None(작성자 컬럼 도입 전의 행)이면 슈퍼유저만
Public · PublicWrite · LoginRequired · SuperuserRequired access.py 뷰의 dependencies=[...] 에 넣는 접근 수준 선언. Public·PublicWrite 는 아무것도 하지 않는 표식 의존성(런타임 비용 없음), 나머지는 위 두 의존성 그대로
AccessPolicyGuard access.py 앱 조립 직후(main.py, 라우터·헬스·Admin 결선 뒤) 모든 APIRoute(숨긴 경로·중첩 include 포함, 문서용 Starlette Route·/admin Mount 제외)의 의존성 트리를 재귀로 훑어 선언 없음·이중 선언·쓰기+Public·조회+PublicWrite 를 모으고, 하나라도 있으면 목록 전체를 담은 AppContractError 로 기동을 멈춘다. require_superuser 는 내부에서 get_current_principal 을 쓰므로 슈퍼유저 하나로 판정
  • 무상태 판정: 보호 라우트는 토큰만 봅니다. 비활성화·강등은 refresh family 폐기(revoke_user)와 짧은 access 만료(기본 15분)로 반영됩니다 — 이미 발급된 access 토큰은 만료까지 남습니다.
  • 소유권은 서비스가 판정합니다. blog·sns·reply·user 서비스는 생성자로 OwnershipPolicy 를 받고, 수정·삭제 메서드가 principal 을 인자로 받아 존재 확인(404) 뒤 판정합니다(403). user 단건 조회· 수정은 사용자 자신이 소유자이며, 존재 확인 전에 판정해 남의 id 로 존재 여부를 떠볼 수 없습니다.
  • 작성자는 서버가 채웁니다. 생성 시 author_id = principal.id, author = principal.username. 요청 본문의 author 는 무시되고 Update 스키마에는 없습니다. author_id 는 FK 없는 String(36)(인덱스) — 사용자를 지워도 글은 남습니다.
  • user 의 특권 필드: is_active·is_superuser 는 슈퍼유저만 바꿉니다(본인이면 403 USER_PRIVILEGED_FIELD). 비활성화·강등·삭제는 RefreshTokenStore.revoke_user 로 그 사용자의 모든 refresh family 를 폐기합니다. 생성(POST /users)은 슈퍼유저 전용이고 비밀번호가 필수입니다.
  • 첫 슈퍼유저: API 에는 경로가 없습니다(가입은 항상 일반 사용자). scripts/create_superuser.py 가 background_db_session + core get_password_hasher + UserRepository 로 만들거나 승격합니다 (README "첫 관리자 만들기").
  • 접근 수준의 정본은 뷰 선언이고, 기본 정책은 거부입니다. 선언하지 않은 뷰는 열린 채 배포되는 대신 서버가 뜨지 않습니다. 데코레이터 선언만으로는 "선언을 잊은 뷰" 를 막을 수 없어 기동 검사를 둡니다. 함수를 감싸는 @login_required 식 데코레이터는 쓰지 않습니다 — FastAPI 는 뷰 시그니처로 주입·검증· OpenAPI 를 만들기 때문에 감싸면 셋이 함께 깨집니다. 핸들러 인자 CurrentPrincipal·SuperuserPrincipal 은 선언으로 인정되므로 같은 수준을 데코레이터에 중복으로 적지 않습니다. 예시 정책이 의도대로인지는 tests/test_authorization.py 의 EXPECTED 표(README 권한 표와 같은 내용)가 가드의 판정·OpenAPI security 표시와 대조해 고정합니다. 소유자 판정은 선언이 아니라 서비스 동작이라 같은 파일의 실요청 테스트가 맡습니다.

10.3 SQLAdmin

  • /admin 은 활성 슈퍼유저 로그인이 필요합니다(admin-login ADR-002). create_admin_interface() 가 AdminAuthBackend(app/features/auth/admin_auth.py)를 주입합니다. 로그인은 API 로그인과 같은 verify_credentials(Argon2·bcrypt 재해시·비활성 거부)를 쓰고, 슈퍼유저가 아니면 실패입니다. 실패 사유는 구분하지 않습니다(400). 시도 수는 API 와 같은 AUTH_LOGIN_* 한도로 키를 따로 셉니다 (admin:rl:, 초과 시 로그인 화면을 429 + Retry-After 로).
  • 세션은 /admin 하위 앱에만 붙은 Redis 서버 세션입니다(app/core/security/admin_session.py — 저장소 AdminSessionStore, ASGI 미들웨어 RedisSessionMiddleware). 쿠키 admin_session(Path=/admin, SameSite=Strict, HttpOnly, Max-Age=절대 만료, staging/production 은 Secure)에는 secrets.token_urlsafe(32) 세션 ID 만 있고, 내용 {"data", "user_id", "created_at"} 은 Redis admin:sess:{HMAC-SHA256(SESSION_SECRET_KEY, ID)} 에 있습니다(TTL = min(미사용, 절대 만료까지 남은 시간), 요청마다 갱신). 사용자별 인덱스 admin:user_sessions:{user_id} 로 한 사용자의 세션을 한 번에 지웁니다. 로그인 성공은 세션을 비우고 사용자 id·새 CSRF 토큰을 넣은 뒤 rotate_session 으로 세션 ID 를 새로 발급하고 이전 키를 지웁니다. 로그아웃·authenticate 거부는 키를 지우고, 사용자 서비스의 비활성화·강등·삭제는 refresh 폐기와 같은 지점에서 AdminSessionStore.revoke_user 를 부릅니다(get_user_service 가 주입, ADMIN_DISABLED=true 면 None). 관리 화면에서 직접 고친 경우는 UserAdmin 의 커밋 전 훅 on_model_change(비활성화·슈퍼유저 해제·비밀번호 해시 변경일 때만, 변경 전후 비교)·on_model_delete 가 UserService 와 같은 판정 revocation_for·폐기 revoke_user_access 를 부릅니다(규칙 한 곳 — 관리 화면 경로 = API 경로). 비활성화·슈퍼유저 해제·비밀번호 해시 변경·삭제면 관리 세션과 refresh 를 모두 끊습니다. Redis 폐기가 실패하면 예외로 커밋이 막혀 DB 변경이 남지 않습니다(fail-closed). 자기 강등은 지금 세션도 끊습니다. 매 요청 DB 확인도 유지합니다(이중 방어). Redis 오류는 503 입니다(fail-closed) — 쿠키 없는 첫 요청처럼 응답 직전에 새 세션을 저장하다 실패해도 같습니다.
  • 세션은 관리 화면 전용입니다. 메인 앱에는 세션 미들웨어가 없고, API 보호 경로는 Bearer 토큰만 봅니다 — 관리 세션 쿠키로 API 를 호출해도 401 입니다. 회귀 가드: tests/test_admin_login.py 의 세션 범위 테스트.
  • 로그인 화면은 app/templates/admin/sqladmin/login.html(Bootstrap 5.3.8 CSS, SRI 고정, JS 없음)이 sqladmin 기본 화면을 덮어씁니다(templates_dir 의 FileSystemLoader 가 먼저 찾는다).
  • CSRF(synchronizer token, 세션에 하나): 템플릿 전역 함수 csrf_token(request)(AdminAuthBackend.csrf_token) 가 세션에 secrets.token_urlsafe(32) 토큰을 둡니다. 로그인 폼은 hidden 필드로 싣고 login() 이 레이트 리밋·자격 확인 전에 csrf_valid(bytes hmac.compare_digest)로 비교합니다. 로그인 이후의 모든 POST·PUT·PATCH·DELETE(생성·수정·삭제·일괄 삭제·가져오기·로그아웃)는 하위 앱의 AdminCsrfMiddleware 가 헤더 X-CSRF-Token 또는 폼 필드 csrf_token(본문 버퍼링 후 receive 재생)을 같은 함수로 비교해 403 으로 막습니다(로그인 POST 는 건너뜀 — 검사는 한 번). 버퍼링하는 폼 본문은 10 MiB 까지입니다 — Content-Length 로 먼저, 없거나 거짓이면 읽는 도중 누적 크기로 판정해 넘으면 413, 1 MiB 를 넘는 필드(starlette 폼 파서 기본 상한)나 깨진 폼은 400 입니다(e2e-policy-2 결정 7, 상한은 admin_auth.py 의 상수). 토큰은 app/templates/admin/sqladmin/base.html(원본 sqladmin_original/base.html 상속, head_tail 블록만 추가)의 meta 와 인라인 스크립트가 폼 제출·XHR·fetch 에 붙입니다. 로그아웃은 _make_logout_post_only 가 POST 전용으로 바꾸고(GET 405) 스크립트가 링크를 POST 폼으로 바꿉니다. sqladmin 원본이 어긋나면 test_packaged_templates_still_fit_the_base_override 가 실패합니다.
  • 목록 날짜 필터: created_at 이 있는 모든 뷰가 core 의 LocalDateFilter(app/core/admin_filters.py)를 씁니다. 입력 YYYY-MM-DD 를 TIME_ZONE 의 [자정, 다음 자정) 으로 보고 UTC aware 범위로 바꿔 질의합니다 (같은 날 / 이후(포함) / 이전(미포함) / 기간 YYYY-MM-DD~YYYY-MM-DD — 시작일 00:00 ≤ t < 종료일 다음날 00:00, 한쪽만 있으면 열린 구간, 역순·형식 오류는 필터 미적용). 전용 템플릿 sqladmin/filters/local_date_filter.html(sqladmin 이 필터 객체의 template 을 include 한다)이 날짜 입력 두 개를 한 값으로 합쳐 보내고, 빠른 선택(오늘·최근 7일·30일)은 기간 링크입니다. 기본 OperationColumnFilter 는 UTCDateTime 을 날짜로 보지 못해 문자열을 바인딩하고 500 이 났습니다. 잘못된 입력은 필터 없이 목록을 보여 주고 WARNING 을 남깁니다.
  • ADMIN_DISABLED=true 면 /admin 이 아예 없습니다(404). sqladmin·관리 세션 미들웨어·인증 백엔드를 만들지 않고 OpenAPI·/docs·오류 응답·헤더·기동 로그 어디에도 관리 경로가 나오지 않습니다 (tests/test_admin_disabled.py). 관리 화면을 쓰지 않는 배포는 끕니다.
  • User.hashed_password 는 목록·상세·폼·내보내기 어디에도 나오지 않고, User 는 Admin 에서 생성할 수 없습니다(비밀번호 없는 계정 방지). 구조 증거: tests/core/test_admin_views.py.
  • 설계·흐름도·위협 모델·운영 절차 전체: admin 인증 안내서.

10.4 현재 한계 — 외부 공개 전에 결정할 것

항목 현재 상태
권한 모델 슈퍼유저/일반 2단계뿐이다(세분화된 역할·그룹 없음). 강등·비활성화는 access 만료(기본 15분)까지 반영이 늦다
작성자 작성자 컬럼 도입 전의 글(author_id NULL)은 슈퍼유저만 수정한다. author 표시 이름은 작성 시점의 username 이라 이름을 바꿔도 따라가지 않는다
참조 무결성 Reply.post_id 는 FK 없는 문자열 — 게시글 존재 검증·삭제 전파 정책 없음
로그인 보호 고정 창 rate limit(창 경계에서 최대 2배 통과, API·/admin 공통). 계정 잠금은 없다
관리 세션 Redis 서버 세션 — 로그아웃·강등·비활성화·삭제(API·관리 화면 모두)는 서버에서 즉시 폐기된다. Redis 장애 중에는 관리 화면이 503 이다. sqladmin 의 사용자 정의 @action 은 GET 이라 CSRF 검사 대상이 아니다(이 저장소에는 없다). 관리 화면에서 직접 편집한 강등은 다음 요청의 DB 확인으로 끊긴다
토큰 폐기 refresh 는 family 단위로 폐기된다(재사용 탐지·로그아웃). access 토큰은 만료(기본 15분)까지 유효하다
접속 로그 개인정보 query_string 은 민감 키 값만 가리고 나머지와 referer·session_id 쿠키는 원문 저장한다 — 사용자 결정으로 유지(log-redaction-fixes ADR-003). 보존 기간은 ACCESS_LOG_RETENTION_DAYS(기본 365일, beat 가 매일 삭제 — §7.1). 조회 API 는 슈퍼유저 전용
CORS 기본 CORS_ALLOW_ORIGINS=["*"], credentials false (staging/production 은 게이트가 * 를 거부)
