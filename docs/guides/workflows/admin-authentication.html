1. 개요·범위: 두 인증 체계와 세션의 적용 범위

이 저장소에는 인증 체계가 둘 있다. API(/api/...)는 OAuth2 password 흐름으로 받은 JWT Bearer access 토큰을 쓰고, 관리 화면(/admin, SQLAdmin)은 Redis 서버 세션을 쓴다 — 브라우저 쿠키 admin_session에는 무작위 세션 ID 만 있고 내용은 Redis 에 있다(admin-session-hardening ADR-001). 둘은 저장 위치·수명·폐기 방식이 다르고 서로를 대신하지 않는다.

확인 결과 — 세션은 /admin 전용이다(admin-login ADR-008). 앱 전역 세션 미들웨어는 없다. RedisSessionMiddleware와 AdminCsrfMiddleware는 SQLAdmin 하위 앱(/admin 마운트) 안에만 있고, API 의 인증 의존성 get_current_principal은 Authorization: Bearer 헤더만 본다(app/core/security/dependencies.py oauth2_scheme). SESSION_COOKIE_NAME(기본 session)은 접속 로그 미들웨어가 쿠키 값을 session_id 열에 기록용으로만 읽는다 — 인증에 쓰지 않는다. Celery 태스크·스크립트도 세션을 쓰지 않는다.

이 확인은 테스트로 고정돼 있다: tests/test_admin_login.py 의 test_session_middleware_lives_only_in_the_admin_sub_app(메인 앱 user_middleware에 없고 하위 앱에만 RedisSessionMiddleware, 서명 쿠키 SessionMiddleware는 어디에도 없음), test_admin_session_cookie_does_not_authenticate_the_api(Redis 에 살아 있는 세션 ID 쿠키만으로 /api/v1/auth/me는 401), test_admin_session_cookie_is_never_set_outside_admin, 그리고 같은 쿠키가 실제로 유효한 관리 세션임을 보이는 대조군 test_planted_session_id_is_a_valid_admin_session.

SESSION_SECRET_KEY의 의미가 바뀌었다: 예전에는 쿠키 서명 키였고, 이제는 세션 ID 를 Redis 키로 바꾸는 HMAC-SHA256 키다(admin:sess:{HMAC(SESSION_SECRET_KEY, sid)}). 소비처는 ① get_admin_session_store(app/core/security/dependencies.py — 관리 하위 앱과 사용자 서비스가 같은 provider 를 쓴다), ② 설정 검사(config.py 의 validate_env_source·validate_deployment_safety), ③ 로그 마스킹(config.LOG_SECRET_SETTINGS — 값 원문이 로그에 나오면 가린다)이다. 키를 바꾸면 기존 Redis 키를 찾지 못하므로 모든 관리 세션이 무효가 된다.

2. 구성도와 주입 관계

메인 FastAPI 앱의 미들웨어 체인을 지난 요청은 경로에 따라 갈린다. /api는 라우터와 JWT 의존성으로, /admin은 SQLAdmin 이 만든 Starlette 하위 앱으로 간다. sqladmin 은 authentication_backend.middlewares를 하위 앱 생성에 넣는다(sqladmin 0.32 Admin.__init__). AdminAuthBackend는 부모 생성자(서명 쿠키 SessionMiddleware를 만든다)를 부르지 않고, 그 목록을 [RedisSessionMiddleware, AdminCsrfMiddleware]로 직접 둔다 — 세션이 바깥, CSRF 검사가 안쪽이라 CSRF 가 세션의 토큰을 읽는다.

협력 객체는 모두 생성자 주입이다. 조립은 app/features/admin.py 한 곳이 하고(build_admin_auth_backend, create_admin_interface), 테스트는 authentication_backend= 인자로 세션 팩토리·Redis·세션 저장소만 바꾼 백엔드를 넣는다. Redis 는 lifespan 이 app.state.redis 에 두므로 생성 시점이 아니라 요청 시점에 꺼낸다 — 하위 앱 안의 request.app은 메인 앱이 아니라서 get_redis(request)를 쓸 수 없다. 세션 저장소는 요청마다 get_admin_session_store(app.state.redis)로 만든다(사용자 서비스의 폐기 훅과 같은 provider). 클라이언트가 없으면 RedisError를 올려 미들웨어가 503 으로 끝낸다.

코드 근거: admin.py · create_admin_interface · admin_auth.py · AdminAuthBackend·AdminCsrfMiddleware · user_dependencies.py · get_user_service · main.py

3. 기동 결정 흐름: ADMIN 잔존 검사와 ADMIN_DISABLED 분기

예전 설정 ADMIN(true=켬)은 ADMIN_DISABLED(true=끔, 기본 false)로 바뀌었다(ADR-006). Settings 는 extra="ignore"라 남은 ADMIN을 조용히 버리는데, 그러면 ADMIN을 false로 두어 끄려던 배포가 관리 화면을 켠 채 뜬다. 그래서 validate_renamed_settings()(config.py)가 환경 변수와 .env 키를 대소문자 무시로 보고, 남아 있으면 기동을 멈춘다. 호출 순서는 config.py 끝의 세 줄(validate_env_source → validate_renamed_settings → validate_deployment_safety). ENV=test는 다른 검사와 마찬가지로 건너뛴다.

main.py 의 if not app_settings.ADMIN_DISABLED: 블록이 분기한다. ADMIN_DISABLED=true면 app.features.admin을 import 하지 않으므로 sqladmin·AdminAuthBackend·관리 세션 미들웨어가 하나도 만들어지지 않는다(ADR-007).

4. 로그인 시퀀스

로그인 화면은 app/templates/admin/sqladmin/login.html이다. sqladmin 은 템플릿 로더를 ChoiceLoader([FileSystemLoader(templates_dir), PrefixLoader({"sqladmin_original": ...}), PackageLoader("sqladmin", "templates")]) 순서로 만들므로(sqladmin 0.32 Admin.init_templating_engine) templates_dir의 같은 이름 파일이 기본 화면을 덮어쓴다. 로그인 화면은 base 를 확장하지 않는 독립 HTML 이며 Bootstrap 5.3.8 CSS 만 SRI 로 불러온다. JavaScript 는 없다.

  1. GET 으로 로그인 화면을 그릴 때 템플릿 전역 함수 csrf_token(request)(AdminAuthBackend.csrf_token)가 세션에 토큰이 없으면 secrets.token_urlsafe(32)로 만들어 넣고 hidden 필드 csrf_token에 싣는다. 세션이 바뀌었으므로 RedisSessionMiddleware가 새 세션 ID 를 발급해 Redis 에 저장하고 쿠키를 붙인다(익명 세션 — user_id 없음).
  2. POST /admin/login은 AdminCsrfMiddleware가 건너뛴다 — 로그인 검사는 백엔드가 한 번만 한다(중복 검사 없음).
  3. login()이 폼의 csrf_token을 세션 값과 csrf_valid(bytes hmac.compare_digest)로 비교한다. 없거나 다르면 403 으로 로그인 화면을 다시 그리고 레이트 리밋·자격 확인을 건드리지 않는다.
  4. IP 키(AUTH_LOGIN_IP_MAX_ATTEMPTS)와 IP+사용자명 키(AUTH_LOGIN_MAX_ATTEMPTS)를 admin:rl: 접두사로 센다.
  5. verify_credentials(API 로그인과 같은 함수)가 더미 해시·재해시를 처리하고, 슈퍼유저가 아니면 실패한다.
  6. 성공이면 사용자 키 카운터를 지우고 session.clear() 후 user_id와 새 CSRF 토큰을 넣고 rotate_session(request)를 부른다(scope 표시).
  7. 응답 시작 때 미들웨어가 표시를 보고 새 세션 ID 를 발급하고 이전 Redis 키를 지운다(세션 고정 방지). 새 키에 {"data", "user_id", "created_at"}를 TTL=min(미사용 만료, 절대 만료)로 쓰고, admin:user_sessions:{user_id} SET 에 키를 올린다. 쿠키 Max-Age 는 절대 만료와 같다.

코드 근거: admin_auth.py · login · admin_session.py · rotate_session · auth_service.py · verify_credentials · login.html

5. 요청별 인증 흐름

RedisSessionMiddleware가 쿠키의 세션 ID 로 Redis 를 읽는다. 키가 없거나(미사용 만료·로그아웃·폐기) 저장된 created_at에서 절대 만료가 지났으면 빈 세션으로 다루고 응답에서 쿠키를 지운다. 이어서 sqladmin 의 login_required가 AdminAuthBackend.authenticate를 부르고, 세션의 user_id로 매 요청 DB 를 조회해 활성·슈퍼유저가 아니면 세션을 비운다(→ Redis 키 삭제). 응답 시작 때 세션 내용이 바뀌었으면 저장하고, 아니면 TTL 만 min(미사용 만료, 절대 만료까지 남은 시간)으로 다시 맞춘다 — 미사용 만료는 요청마다 다시 세지만 절대 만료는 넘지 않는다.

코드 근거: admin_session.py · RedisSessionMiddleware · admin_auth.py · authenticate · test_each_request_resets_the_idle_ttl·test_absolute_expiry_is_never_extended

7. 로그아웃 흐름

sqladmin 0.32 의 로그아웃 라우트는 GET /admin/logout이다. GET 로그아웃은 다른 사이트가 <img src>로 관리자를 강제로 로그아웃시킬 수 있으므로, create_admin_interface의 _make_logout_post_only가 같은 이름(admin:logout)·엔드포인트의 POST 전용 라우트로 바꾼다(GET 은 405). 화면의 로그아웃 링크(sqladmin layout.html)는 그대로 두고, base.html 덮어쓰기의 스크립트가 그 링크 클릭을 가로채 토큰을 실은 POST 폼으로 제출한다. POST 는 AdminCsrfMiddleware가 토큰을 확인한다.

logout()은 세션을 비운다. 응답 시작 때 미들웨어가 Redis 키를 지우고(사용자 인덱스에서도 제거) 쿠키를 지운다. 그래서 로그아웃 전에 복사해 둔 쿠키 값도 그 순간 무효다.

9. 계정 수명주기와 즉시 폐기

첫 슈퍼유저는 API 로 만들 수 없고 scripts/create_superuser.py로 만든다(대화형 또는 --password-stdin). 이미 있는 사용자명이면 슈퍼유저로 승격한다.

uv run python -m scripts.create_superuser --username admin --email admin@example.com
printf '%s' "$PW" | uv run python -m scripts.create_superuser --username admin --email admin@example.com --password-stdin

API 로 사용자를 비활성화·강등·삭제하면 UserService._revoke_sessions가 refresh family 폐기(RefreshTokenStore.revoke_user)와 관리 세션 전체 폐기(AdminSessionStore.revoke_user — admin:user_sessions:{user_id}의 모든 키와 인덱스 DEL)를 같은 지점에서 한다. 저장소는 get_user_service가 get_admin_session_store로 주입하고, ADMIN_DISABLED=true면 None이라 폐기할 관리 세션도 없다. 비밀번호 변경 API 는 아직 없다(생기면 같은 훅을 부른다).

관리 화면에서 직접 고친 경우는 UserAdmin(app/features/user/admin.py)이 맡는다(admin-session-hardening ADR-008). sqladmin 0.32 는 수정 때 세션 안에서 on_model_change(폼 값 반영 전) → 값 반영 → commit, 삭제 때 on_model_delete → delete → commit 순서로 부른다(sqladmin 패키지의 _queries.py). 그래서 폐기를 이 커밋 전 훅에 둔다: on_model_change가 지금 값과 폼 값(data, 폼에 없는 필드는 그대로)을 판정 함수 revocation_for로 비교한다 — 비활성화·슈퍼유저 해제·비밀번호 해시 변경이면 관리 세션과 API refresh 를 모두 끊는다. on_model_delete도 둘 다 끊는다. 판정 revocation_for와 폐기 revoke_user_access는 API UserService.update_user·delete_user와 같은 함수다(app/features/user/services/user_service.py) — 이 저장소 안에서 관리 화면 경로와 API 경로의 결과가 같다(ADR-010). Redis 저장소는 세션 미들웨어가 요청 scope 에 둔 것(session_store_of)이고, refresh 저장소는 같은 Redis 로 get_refresh_token_store가 만든다.

Redis 오류면 커밋하지 않는다. 훅 예외가 commit 앞에서 올라가 세션이 롤백되고, sqladmin 은 그 예외를 수정 화면 오류(400)·목록 error 표시로 그린다. 그래서 "DB 는 비활성화됨 + 세션은 살아 있음" 상태가 남지 않는다(API 의 UserService도 폐기를 커밋 전에 한다). 한쪽 폐기가 끝난 뒤 다른 쪽이 실패하면 일부만 끊긴 채 DB 는 그대로다 — 다시 로그인하면 되는 안전한 쪽이다. 같은 요청 끝의 세션 저장은 SET XX(키가 있을 때만)라 방금 폐기한 자기 세션을 되살리지 않는다.

12. 확장 시 주의

  • 새 관리 뷰: 기능 폴더의 admin.py에 admin_views를 두면 registry 가 등록한다(scripts/new_app.py --with-admin). 인증·세션·CSRF 는 하위 앱 전체에 걸리므로 뷰마다 다시 구현하지 않는다. created_at이 있으면 LocalDateFilter(같은 날·이후·이전·기간)를 붙인다.
  • 상태를 바꾸는 사용자 정의 action: sqladmin @action은 GET 라우트라 CSRF 검사 대상이 아니다. 상태를 바꾸는 작업은 action 대신 폼(POST)으로 만든다.
  • 템플릿 덮어쓰기: base.html은 head_tail 블록만 덧붙인다. 다른 sqladmin 템플릿을 덮어쓸 때 head_tail을 덮어쓰면 토큰 스크립트가 빠진다(test_packaged_templates_still_fit_the_base_override). 로그인 화면은 독립 HTML 이며 hidden 필드 csrf_token을 지우면 모든 로그인이 403 이다.
  • 세션에 넣는 값: 세션은 Redis 에 평문 JSON 이다. 비밀을 넣지 않는다. 키 user_id는 사용자 인덱스·폐기에 쓰인다.
  • 새 폐기 지점: 비밀번호 변경 등 세션을 끊어야 하는 서비스는 get_admin_session_store를 주입받아 revoke_user를 부른다(None이면 관리 화면이 꺼진 것).
  • 세션을 API 에 쓰지 않는다: 앱 전역 세션 미들웨어를 추가하거나 API 의존성이 쿠키를 읽게 하면 test_session_middleware_lives_only_in_the_admin_sub_app·test_admin_session_cookie_does_not_authenticate_the_api가 실패한다.
