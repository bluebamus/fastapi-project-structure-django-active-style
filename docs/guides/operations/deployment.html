배포와 운영

배포 전 점검, 관측, 장애 대응입니다.

허브 부팅 설계 API 설정 요청 인증 기능 개발 테스트 운영

도식은 고정 버전 Mermaid CDN을 사용합니다. 인터넷이 없어도 본문·표·도식 원문을 읽을 수 있습니다.

배포 전 필수 확인

  • ENV=staging 또는 production 으로 둡니다. 이때 DEBUG=true·CORS_ALLOW_ORIGINS 의 *·LOG_SQL_ECHO_ENABLED=true·LOG_LEVEL=DEBUG 는 기동 거부입니다. 비밀 키 3종(32자 이상, access≠refresh)과 MYSQL_PASSWORD 는 모든 ENV 에서 실제 값이어야 합니다.
  • 접속 정보는 URL 이 아니라 개별 키로 주입합니다: MYSQL_HOST·MYSQL_PORT·MYSQL_USER·MYSQL_PASSWORD·MYSQL_DATABASE, REDIS_HOST·REDIS_PORT·REDIS_DB·REDIS_PASSWORD. URL 설정은 마이그레이션용 ALEMBIC_DATABASE_URL(선택) 하나뿐입니다. .env 없이 주입하면 필수 8개가 모두 있어야 합니다.
  • DEBUG=false 면 create_all 을 하지 않으므로 uv run alembic upgrade head 를 rollout 과 호환되는 순서로 먼저 실행합니다.
  • staging/production 의 /admin 세션 쿠키는 Secure 라 HTTPS(프록시의 TLS 종료 포함)가 필요합니다. 관리 화면을 쓰지 않으면 ADMIN_DISABLED=true.
  • 프록시 뒤면 TRUSTED_PROXY_HOPS 를 앞단 프록시 단 수로 둡니다. 0 이면 모든 사용자가 프록시 IP 하나로 보여 로그인 rate limit 을 함께 맞습니다.
  • 첫 슈퍼유저를 uv run python -m scripts.create_superuser 로 만듭니다.
  • Redis 7.0 이상이 필요합니다. Celery worker 와 beat 를 같은 코드·설정으로 띄웁니다 — beat 가 없으면 접속 로그 보존 삭제가 돌지 않습니다.
  • /health 는 생존(liveness), /ready 는 writer DB·Redis 확인(readiness, 실패 503)에 씁니다.

전체 점검표는 README 운영 배포가 정본입니다.

운영 관측과 장애 대응

  • 요청 식별자는 따로 두지 않습니다. 오류 로그의 route template·메서드·상태·error_code 와 접속 로그(DB)의 시각·user_id·IP·경로·상태·처리 시간을 시각 기준으로 맞춰 봅니다.
  • 5xx 증가, /ready 실패, DB pool 고갈, Redis 오류, Celery 적체를 알림 대상으로 둡니다.
  • Redis 장애: 기동 중이면 시작하지 않습니다. 실행 중이면 Redis 를 쓰는 요청(가입·로그인·refresh·logout, 사용자 수정·삭제의 세션 폐기, /admin)이 503, /ready 가 503 이고, Redis 를 쓰지 않는 조회 API 는 계속 응답합니다. 인증 저장소 오류를 허용으로 우회하지 않습니다.
  • 종료 시 lifespan 이 background 작업·Redis·DB 엔진·로그 큐를 등록 역순으로 정리합니다. grace 기간은 가장 긴 정상 요청과 정리 시간을 근거로 정합니다.
